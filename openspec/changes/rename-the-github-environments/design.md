## Context

**Three of the four things this change touches are repository settings, and nothing committed can see them.** `.github/tests` may not make a network call — a constraint that suite asserts of itself — so no check in this repository can establish that an Environment exists, that it holds a secret, or that it requires a reviewer. The executable verification this change owes is therefore small and almost beside the point; the verification that matters is a sequence of operator observations, and the sequencing exists to make each failure loud at the moment it happens rather than several steps later.

**The live state, measured 2026-09-13 rather than assumed.** `main-production` already exists, created by hand on 2026-09-12 as `rename-the-external-services`'s probe of whether an Environment can be renamed; it carries the required reviewer and no secrets. `production` holds 15 secrets and its reviewer, `staging` holds 6 and no protection rules by design, and `main-staging` does not exist. The `handoff.md` in this change records the same table and an earlier reading of it that was already stale, which is why every task below re-reads rather than trusting a recorded number.

**The premise the queue entry was written on has turned out to be false, and it was the expensive half.** Entry 75 priced this change as a rotation of three SSH private halves, on the strength of `docs/bootstrap-a-new-host.md` §0.3 instructing the operator to delete the local private half once it is stored in GitHub. That instruction was not followed: `~/.ssh/shatynska-ansible-ci-main-production`, `~/.ssh/shatynska-ansible-ci-main-staging` and `~/.ssh/shatynska-platform` are all present and unencrypted, and the last of them derives a public half byte-identical to the `deploy_apps` entry committed in `ansible/inventory/group_vars/production.yml`. The two converge keys cannot be proven from the repository — their public halves are recorded in no committed file, only in each host's `/root/.ssh/authorized_keys` — so this design keeps the handoff's rule and proves them by login before anything old is deleted.

**Two mechanical facts decide the order**, both measured by `rename-the-external-services` on 2026-09-12. `gh secret set --env <name>` fails loudly on an unknown Environment, with a `404` from the public-key fetch. A workflow's own `environment:` key does the opposite: GitHub **creates** the Environment it names, with no protection rules, and runs. So a flip that lands before its Environment is populated and protected does not fail — it deploys unreviewed.

## Goals / Non-Goals

**Goals:**

- Both GitHub Environments named for their stacks — `main-production`, `main-staging` — with the reviewer on the production one throughout, never for a moment absent while a job can name it.
- Every secret value carried over rather than rotated, with one stated exception: the Tailscale OAuth pair, which cannot be read back and is replaced by a newly created client. No host is touched and no `authorized_keys` is edited by hand, and nothing holds a dead credential at any point.
- The naming scheme delivered whole, and `docs/naming-conventions.md`'s exception banner deleted rather than reworded.
- Every commitment this repository made to entry 75 discharged in the same change that makes it true.

**Non-Goals:**

- **Rotating any credential that can be carried over.** Where a value is present it is re-entered unchanged, and only the Tailscale OAuth pair — which genuinely cannot be read back from anywhere — is replaced. A rotation is a separate decision with its own risk and does not belong in a rename, so this change replaces exactly what it must and says which.
- **Touching the environment axis.** `target_environment`, the Ansible groups `production` and `staging`, the `group_vars` filenames, the `--vault-id` labels and the inventory sources all stay as they are. They name the environment, and the environment is what they mean.
- **Renaming any requirement or scenario.** The retired-requirement-name sweep exists because a rename orphans every citation of the old name, and this change has no reason to pay that. Only requirement *texts* move.
- **Closing entry 77.** Three workflows gate on one Environment and render identical approval prompts; that is a real defect and it is that entry's, not this one's. This change makes the prompts say `main-production` instead of `production` and leaves them as indistinguishable from one another as they were.

## Decisions

### Create, populate, protect, verify — and only then point

The ordering follows directly from the asymmetry above. Every Environment is fully built and observed before any committed file names it, because the failure mode of the opposite order is silent. Concretely, per stack: create the Environment if absent; set every secret it needs; set its protection rules to match what the old Environment had; re-read all three through the API; and only then commit the `github_environment` flip.

**This ordering transiently puts each stack's write token in two Environments, and that is worth naming rather than leaving for a reader to notice.** *Write Credentials Confined to the Gated Pipeline* (`openspec/specs/iac-safety-hardening/spec.md`) says the token "SHALL exist in exactly one location: that stack's own GitHub Environment secret". Between populating a new Environment and deleting the old one, `HCLOUD_TOKEN` exists in both — only one of which the stack declares, so only one is reachable by any job. The window is bounded at each end by a task, it is the unavoidable cost of creating before pointing, and the alternative — deleting the old Environment first — is the ordering whose failure mode is an unreviewed production apply. It closes at the deletion.

This also means `main-production`'s reviewer is verified *now*, not at the end. It carries one today, but "it carries one today" is exactly the kind of claim this change was handed as true and found stale.

### Staging goes first, in its own pull request

Staging's half is six secrets, none unrecoverable, and its Environment deliberately requires no reviewer — so the whole create-populate-verify-flip-observe sequence can be exercised where a mistake costs a re-run rather than a production approval. Its flip touches five files: `terraform/stacks/main-staging/pipeline.yml`, that stack's `versions.tf`, and all three name sets — in `.github/tests/test_a_second_environment.py` (which also holds the `SECOND_ENVIRONMENT_GITHUB_ENVIRONMENT` literal), `.github/tests/test_host_converge_workflow.py` and `.github/tests/test_environment_agnostic_pipeline.py`. All three move here rather than with production because the identifier collapse below happens at *staging's* flip: `staging` leaves every one of those sets the moment that declaration moves. An earlier draft of this paragraph said three files and named two of the three sets — the same counting-rather-than-sweeping slip recorded below, made twice about the same modules, which is why task 4.2 now sweeps for them.

Production's half then follows in a second pull request carrying everything else — the other two test literals, `platform-deploy.yml`'s literal, the spec deltas, the documentation and the commitment deletions. Splitting it this way keeps the canary honest: if staging's flip is bundled with production's, the first time the sequence runs is against the stack that waits on a human.

**The alternative — one pull request for both — was rejected** for that reason alone. It is fewer merges and it is the only version of this change in which a sequencing mistake is discovered on production.

### Populate by reading the old Environment's *names* and the operator's own values

A secret's value cannot be read back out of GitHub, so "copy the Environment" is not an operation that exists. What is enumerable is the *set of names*, and the design uses that as the checklist: 15 on `production`, 6 on `staging`, re-read from the API rather than from this document, because a secret added between the writing and the doing would otherwise be silently dropped.

**A one-shot gated workflow that reads each secret under the old Environment and writes it to the new one through the API was considered and rejected.** It would make the copy exact and avoid every recovery question below. It also requires granting the repository's GitHub App `secrets: write`, and leaves in the repository — even briefly — a workflow whose whole purpose is to read every production secret and write it somewhere. The values are all obtainable without it, so the capability is not worth creating.

### The four missing values are recovered wherever they can be, and only one pair is reissued

The operator's audit found four absent from the password manager. Three of them turned out not to be missing at all, once the question asked was *where else does this value exist* rather than *is it in the password manager*:

- **`PLATFORM_ACME_EMAIL` and `PLATFORM_DEPLOY_HOST` are readable off the running deployment.** Neither is really a secret — one is an address Let's Encrypt was registered with, the other is how CI reaches the host — and both are present in the platform stack's rendered environment on the production host. Reading them back is exact; regenerating them is not even meaningful for the second.
- **`TF_API_TOKEN` is on the workstation**, in `~/.terraform.d/credentials.tfrc.json`, where `terraform login` put it. `docs/change-queue.md` entry 75 recorded this and an earlier draft of this design contradicted it, asserting the token could not be read back. Entry 75 was right. This is the same class of premise this change disproved for the SSH keys — *a document said the value was gone, and the value was not gone* — and it was missed one section after being caught, which is worth recording rather than quietly correcting.
- **Only the Tailscale OAuth pair is replaced.** A client secret is shown once at creation and nowhere afterwards, so there is no location to read it from and a new client in the Tailscale admin console is the only path.

**One OAuth client serves both Environments — and, it turns out, every repository.** `docs/bootstrap-a-new-host.md` records it as "the same client's values in both" and, at three further places, as one client serving *every* repository with each application repository holding the same two values — so a replacement reaching one Environment breaks the other. An earlier draft of this design reissued the client late, to shrink the window in which the still-live Environments held a dead pair, and would thereby have left `main-staging` — populated earlier from the old client — holding an invalidated credential permanently, discovered by a failed converge some time after the change was archived. The fix removes the window rather than shrinking it: **create** the new client before either new Environment is populated, populate both from it, and treat revoking the old one as a separate question with a wider blast radius than this change's scope. **The default is to leave it live.** An application repository bootstrapped per the runbook holds either that same client or "a second one with the same tag" — the runbook says both things in different places, so the question is per-repository and is not settleable from the runbook at all. Worse, it cannot be settled from GitHub either: a secret's value cannot be read back, which is this change's founding premise, so another repository can be shown to hold *a* client and never *the old* one. A condition whose permissive branch is reached by looking and finding nothing is not a safeguard, so the condition is inverted — revoke only on a positive enumeration of every holder, and otherwise record the decision and move the question to the queue. Two clients coexist for longer than is strictly necessary, and that is the point — no ordering mistake inside that span can produce a dead credential, where every alternative ordering has a window in which one exists.

**`TF_API_TOKEN` carries a wrinkle that survives the good news.** It exists as a repository secret *and* an Environment secret holding an identical value, per *HCP Terraform Access via a Static Token, Unsplit by Privilege*, and that requirement obliges the two to match. Writing the new Environment's copy from the workstation file without also rewriting the repository-scoped one would satisfy every check and quietly break that obligation, because an Environment secret missing entirely falls back to the repository one and passes. So both are written from one source in adjacent tasks, and the secret count is re-read afterwards. This is the one secret whose *omission* this pipeline does not catch.

### The two observations that prove the credentials need triggers this change creates

A production apply is raised by the production pull request itself, because that pull request changes `terraform/stacks/main-production/`. The other two are not, and this was nearly missed:

- **`host-converge.yml` triggers on `ansible/**` and the production pull request touches no such file.** It does carry `workflow_dispatch`, so the converge observation is a deliberate dispatch after the merge rather than something the merge produces.
- **`platform-deploy.yml` triggers only on a push to `main` touching `platform/**`, and carries no `workflow_dispatch` at all.** There is no way to ask for it — but no edit has to be manufactured either, because `platform/README.md` describes "a `production`-Environment-gated job" and is therefore a file this change must correct anyway. Correcting it raises the deploy. An earlier draft of this design added a comment-only edit to the Compose file for the trigger, having not noticed that the sweep would force a `platform/**` correction regardless; the manufactured edit was removed rather than kept alongside it.

Without those two triggers the observations cannot be made, and the deletion in the last section would be taken on three claims of which one was tested. Since the Tailscale pair is replaced and the deploy key re-entered, the deploy observation is the *only* thing that tests either on production.

**The staging converge is dispatched in section 4, not section 8, and the ordering is the whole point of a canary.** An earlier draft placed it after production had been populated, flipped and observed — which made the first real exercise of a freshly created OAuth client the gated production deploy, on a trigger that cannot be re-raised. Dispatching it immediately after staging's flip costs nothing (that workflow takes a `stack` input and `main-staging` is already flipped) and moves the discovery of a mis-scoped client to a run nobody had to approve. Staging's apply, the only other observation in that section, touches neither Tailscale nor SSH, so without this the canary exercises none of the credentials the change re-enters.

### Three identifier sets must gain a third spelling in the same commit as the flip

Three name sets in `.github/tests` are built as the union of the stack directory names and the declared `github_environment` values, and every one of them collapses when those two sources converge. The first is `environment_identifiers()` in `.github/tests/test_a_second_environment.py`, which feeds an assertion tracing to the scenario "The record covers an environment added after it was written" in *Write Credentials Confined to the Gated Pipeline* (`openspec/specs/iac-safety-hardening/spec.md`). Today those two sources give `{main-production, main-staging, production, staging}`. After the flip they give `{main-production, main-staging}` — and the words that drop out are exactly the ones the README and `AGENTS.md` use in prose, so the check would go green by losing its subject.

The second is the inline set in `.github/tests/test_host_converge_workflow.py`'s workflow sweep. The third is inside `test_the_gate_names_no_environment` in `.github/tests/test_environment_agnostic_pipeline.py`, and it is the one this design got wrong: an earlier draft asserted that module "already learned this lesson and reads the group explicitly". That is true of **one** of its two sets — `_names()`, whose comment names entry 75 as the collapse it was defending against — and false of the other, which was simply not counted. The assertion the third set serves is *Each Stack Declares Its Own Pipeline Configuration*'s prohibition on a workflow naming an environment in a condition, so its collapse would stop reporting a gate step conditioned on a literal `production`.

The declared `target_environment` is added as a third source to all three, in the same commit as the flip. The set is then the union of three spellings because an environment genuinely has three — a directory, a GitHub Environment and an Ansible group — and this change is what makes them stop coinciding.

### The old Environments are deleted last, after observation and after the queue is drained

Deleting `production` destroys 15 secret values irrecoverably, and it is the only irreversible step in the change. It happens after a real merge has been observed gating on the new Environments — not after a green pull request, which establishes nothing about repository settings.

**A pending approval raised before the flip is the case that turns the deletion into a defect.** Such a run executes the commit it was raised on, which names `production`; approved or re-run after the deletion, it names an Environment that no longer exists — and GitHub creates the Environment a job names, with **no protection rules**. That is an ungated production job, arriving after the ordering that exists to prevent it has completed. `gh run list --status waiting` showing nothing pending against either old Environment is therefore a precondition of the deletion rather than a courtesy check, and the Environment list is re-read some hours later rather than immediately, because a resurrection is not instantaneous.

**An Environment nothing names is inert, so the deletion may soak.** After both flips have merged, no committed file and no workflow refers to `production` or `staging`, and leaving them in place costs nothing but their continued existence. Waiting days rather than minutes converts the one irreversible step into one taken with days of evidence, and the design deliberately does not require it to be prompt.

## Risks / Trade-offs

**The converge keys are unproven until they are used.** `~/.ssh/shatynska-ansible-ci-main-production` and `~/.ssh/shatynska-ansible-ci-main-staging` are named and dated exactly as the converge keys should be, but nothing in this repository records their public halves, so "this is the key GitHub holds" is an inference. The mitigation is ordering rather than cleverness: the new Environment is populated from these files, a converge is observed to succeed under it, and only then is the old Environment deleted. If the inference is wrong, the converge fails against an Environment nobody has deleted anything for yet.

**`TF_API_TOKEN` fails quietly and `HCLOUD_TOKEN` fails loudly, and the difference is not obvious.** There is no repository-scoped `HCLOUD_TOKEN` — the repository holds `HCLOUD_TOKEN_MAIN_PRODUCTION` and `HCLOUD_TOKEN_MAIN_STAGING` — so an Environment missing it resolves to nothing and the apply dies. `TF_API_TOKEN` is repository-scoped as well, with the same value, so an Environment missing it works. A secret-count re-read after populating is what catches this, and it is a task rather than a note for that reason.

**A merge landing between the populate and the flip is fine; one landing between the flip and the observation is not.** Nothing prevents another change merging mid-sequence. Where that merge touches a stack, it raises that stack's approval under whichever Environment is committed at that moment, which is correct in both halves of the sequence. The real exposure is narrower: between staging's flip merging and its apply being observed, staging applies **unattended** under `main-staging`, as it always does. That is the canary working as intended rather than a risk this change introduces, but it is the reason staging is populated and verified before its flip rather than alongside it.

**The Tailscale pair is the value this design got wrong twice, in opposite directions.** First by reissuing it late, which would have left `main-staging` holding a dead credential; then by planning to revoke the old client once two Environments were gone, on the belief that those two were all that held it. The answer to both is the same: the old client is never invalidated while anything still reads it, and establishing what reads it is a task rather than an assumption. Two clients coexist from creation until somebody has enumerated every holder — possibly permanently, which is an acceptable outcome and is stated as one. Where that is where it ends, the runbook's own credential inventory is corrected to describe two clients with different holders, because this change's record is archived and its queue entry is deleted when taken, and neither is where a future operator looks.

**The converge-key proof does not establish what its name suggests.** A successful login proves the host accepts that key, and the public-half comparison proves the deploy key matches the committed `deploy_apps` entry. Neither proves the file equals the value GitHub stores — nothing outside GitHub can. That is sufficient here, because what the change needs is a key that works, but the task says what it proves rather than claiming more.

**Two changes will disagree about `docs/naming-conventions.md` if they land together.** The banner says whoever archives entry 75 deletes it, and this change does. Anything else editing that file concurrently conflicts. It is a small file and the conflict is textual rather than semantic.
