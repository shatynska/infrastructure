## Why

`docs/naming-conventions.md` records a naming scheme this repository does not yet match. Entry 61 delivered the first quarter of it: the Terraform root became `terraform/stacks/` and the vocabulary around it became *stack*. **That renamed the word. This renames the values.** The directories are still `prod` and `staging`, the server is still `main-server`, the firewall is still `prod-main-server`, the volume is still `main-data` and the SSH key is still `prod` — names chosen before the scheme existed, each of which is wrong in a way the scheme names.

Three of them are wrong in a way that costs something rather than merely reading oddly:

- **`main-server` is unique per Hetzner project and reaches two namespaces that are not.** The tailnet and the heartbeat account hold every stack a company owns, and the server's name reaches both — the tailnet as a machine name, the heartbeat as `<inventory_hostname>-prune-host-images`. A second tenant naming its server `main-server` collides in both, and the heartbeat collision fails green: the live host's weekly success keeps the check while the other host's timer is dead. `docs/bootstrap-a-new-host.md` Appendix C names that masking failure; the scheme's answer is that the server carries its stack's name.
- **`prod` and `preprod` prefix-collide, and `prod` is not what the GitHub Environment, the Hetzner label and the Ansible group would be called if they were chosen today.** The environment axis is spelled in full: `production`.
- **`main-data` is the server's role leaking into a volume's name, and `prod` is a rank word standing in for what an SSH key authenticates.** Project-local resources take the rank axis (`main`); keys take the identity axis (`operator`).

**Nothing here is cosmetic in the sense of being free.** Every rename above is a Hetzner resource, so this change's correctness is established by a pull-request plan that shows each one updated in place rather than replaced. That is the evidence, and it is the reason entry 63 — the HCP workspaces, the GitHub Environments, the repository secrets and the Hetzner projects — is deliberately not here: none of it is provable by a plan.

**One name is now three artifacts, and that is what makes this a change rather than a sweep.** `host-converge.yml` derives a stack's name from `ansible/inventory/<name>.hcloud.yml` and cross-checks `terraform/stacks/<name>/pipeline.yml` and `ansible/inventory/group_vars/<name>.yml` in both directions. Today the stack name, the inventory filename, the Ansible group and the `group_vars` filename are one word by coincidence. After this change the stack is `main-production` and the group is `production`, so the coincidence ends and the derivation has to be replaced by a declaration.

## What Changes

- **The stack directories.** `terraform/stacks/prod/` → `terraform/stacks/main-production/`, `terraform/stacks/staging/` → `terraform/stacks/main-staging/`.
- **The labels on every Hetzner resource.** `environment` is spelled in full (`prod` → `production`; `staging` is already in full), and a `tenant` label joins it with the value `main`. Both modules gain a `tenant` input; both stacks' `hcloud_ssh_key` gains the label directly.
- **Four Hetzner resource names per stack.** The server takes its stack's name (`main-server` → `main-production`, `staging-server` → `main-staging`); the firewall becomes `main`; the volume becomes `main`; the SSH key becomes `operator`.
- **`modules/server` stops deriving the firewall's name.** It builds `"${var.environment}-${var.name}"` today, which after this change would read `production-main-production`. The firewall's name becomes an input of its own, which is also what lets a second firewall in one stack be named on the rank axis beside `main`.
- **The inventory sources and the group variables follow, and they follow to two different names.** `ansible/inventory/prod.hcloud.yml` → `main-production.hcloud.yml` and `staging.hcloud.yml` → `main-staging.hcloud.yml`, because an inventory source belongs to a stack. `group_vars/prod.yml` → `group_vars/production.yml` and `group_vars/staging.yml` stays where it is, because a `group_vars` file belongs to an Ansible group. Both sources gain a `tenant` keyed group, so the scheme's two groups — `main` and `production`/`staging` — both exist.
- **`pipeline.yml` declares the Ansible group its stack's converge targets**, as a new required `target_environment` field, and `host-converge.yml` reads it there instead of reusing the stack name. The stack name still names the inventory source and the concurrency group; the declared value names the play's `hosts:`, the `--vault-id` label and the `group_vars` file discovery cross-checks.
- **Prod's labelled Vault block is relabelled** from `;prod` to `;production`, in place and without the Vault password — the vault id in a `$ANSIBLE_VAULT` header is plaintext metadata outside the authenticated ciphertext. Measured against the pinned `ansible-core` 2.21.3; see design.md decision 8.
- **A new `hostname` role**, which does not exist today. Cloud-init sets a host's name once, at creation, from the Hetzner server name, so renaming the server in Terraform leaves the running host answering to `main-server` forever. The role templates `{{ company }}-{{ inventory_hostname }}` from a single new `group_vars/all.yml` variable that a second company's clone changes once.
- **The `tailscale` role pins the name the host reports to the tailnet** to `{{ inventory_hostname }}`, which nothing pins today — the live host's `Hostname` pref is empty, so the reported name follows the OS hostname this change is about to prefix. The pin is defence rather than mechanism: the tailnet *machine* name is assigned at registration and only the Tailscale interface renames it, which is an operator step. Every CI converge and every platform deploy reaches this host by that machine name, so design.md decision 6 — which records the three reads that established all of this — is the most dangerous part of this change.
- **`.github/tests` literals, `.github/dependabot.yml`'s two Terraform directories**, and the documents that quote any of the above: `README.md`, `docs/bootstrap-a-new-host.md`, both `.envrc.example` files, `docs/deferred-work.md`.
- **Specification text in seven capabilities**, including the three requirement renames entry 61 deferred and the scenario renames it could not take. See design.md decisions 2 and 3 for the mechanism, which is not the one entry 61 used.

## What Does Not Change, and Why Each One Is Named

- **The HCP workspaces, the GitHub Environments, the repository secret names and the Hetzner projects.** These are entry 63. Every one of them is a click in an interface whose effect no file here can verify, and mixing them in would produce one pull request whose green result meant less than it appears to. `pipeline.yml`'s `github_environment` and `read_only_secret` fields keep their present values for the same reason, and so does each `versions.tf`'s `cloud` block.
- **The `/mnt/main-data` mount path.** That is entry 64, which is separated because it costs a stack restart and a monitoring gap, and because the volume's device path is `scsi-0HC_Volume_<id>` — keyed to the volume's id, not its name — so renaming the volume does not disturb the mount at all.
- **`target_environment` and `TARGET_ENVIRONMENT` as names.** They name the Ansible group a converge play targets, which is exactly what they still name. What changes is where the value comes from, not the variable.
- **The `.github/tests` module filenames and test-method names** — `test_environment_agnostic_pipeline.py`, `test_a_second_environment.py`, `test_planned_environment_apply_stage.py` and `test_host_configuration_names_its_environment.py`. They assert nothing about the word in their own names, and renaming them churns several hundred identifiers while changing what no single one checks. Recorded in `docs/deferred-work.md` by entry 61 and left there.
- **The archived change records under `openspec/changes/archive/`.** A record says what was decided and built at the time. `AGENTS.md` permits correcting one only to make it say what actually happened, which a rename is not.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `iac-repo-foundations`: **two requirements.** *Environment and Module Folder Structure* → *Stack and Module Folder Structure*, with its scenario titles carried across by a `REMOVED`+`ADDED` pair — the only mechanism that can rename a scenario (design.md decision 3). *Version Control Excludes State and Secrets* is reached for a scenario body naming the stack directory, not for its title.
- `iac-state-management`: **three requirements.** *Each Environment Has a Dedicated Hetzner Cloud Project* → *Each Stack Has a Dedicated Hetzner Cloud Project*. *Remote State Backend* drops its `infrastructure-<stack>` name derivation, which this change would otherwise make false: the stack becomes `main-production` while the workspace stays `infrastructure-prod` until entry 63. The uniqueness obligation, which is what the requirement is actually for, stays and is strengthened by being stated without a derivation that no file can check. *State Locking* is reached for a scenario body naming the stack directory, not for its title.
- `iac-cicd-pipeline`: **four requirements.** *Each Environment Declares Its Own Pipeline Configuration* → *Each Stack Declares Its Own Pipeline Configuration*, and it gains the `target_environment` field. *Destroy Policy Gate* names `prod` as the stack the gate applies to, and gains a paragraph saying that a rename is not a ground for the override label. *Gated Production Apply Applies the Reviewed Plan* names both stack directories in two scenario bodies — reached because it states the path rule, not because it states a name. *Credential Scoping by Privilege* moves only because it cross-references the renamed requirement by title, which is the one edit a rename cannot leave undone.
- `iac-safety-hardening`: **three requirements**, each naming `terraform/stacks/prod/` or the `main-data` volume: *Provider-Level Deletion Protection*, *Data Durability for Stateful Resources* and *Consistent Resource Labeling*. The last also gains the `tenant` label and the full-spelling rule, which are new obligations rather than renames.
- `iac-server-lifecycle`: **one requirement.** *Conditional Prod Server Creation* keeps its title and gains the stack's new name in its body; `Prod` there abbreviates *production*, which this change does not rename — it spells the environment in full in machine-read values, not in prose titles.
- `iac-data-volumes`: **two requirements**, both keeping their titles for the same reason: *Conditional Prod Volume Creation* and *Volume Attached to Prod Server at Creation*. Both name the volume, which is renamed.
- `iac-host-configuration`: **four requirements, one of them new and one renamed.** *Dynamic Inventory via hcloud Plugin* → *Dynamic Inventory via the hcloud Plugin, One Source per Stack*: it says *environment* for three different things — the source, the group and the `group_vars` file — which was correct at one tenant and is what this change separates. *Host Configuration Names the Environment It Targets* gains where an unattended run takes that value from. *Platform Data Volume Is Mounted at a Fixed Host Path* names the volume and gains the rule that discovery is not keyed on its name. **ADDED**: *The Host's Own Name Is Set by the Converge*, which is the `hostname` role and the tailnet-name pin.

Two capabilities are untouched. `iac-platform-services` names no stack, no label and no Hetzner resource name. `iac-platform-deploy-pipeline` names the GitHub Environment it reuses, which entry 63 owns, and reaches the host through a secret whose *value* this change changes without changing the requirement that describes it.

**Three scenario titles stay wrong, and the tool is why.** A scenario can be renamed only by removing and re-adding the requirement that holds it, and a requirement cannot be removed and re-added under its own name — so a scenario title can move only where its requirement's title moves too (design.md decision 3). *Version Control Excludes State and Secrets*, *Remote State Backend* and *Provider-Level Deletion Protection* each keep a scenario title saying *environment* where it means *stack*, or *non-prod environment* where it means *a stack that is not production*. Renaming their requirements to reach the scenario titles would be renaming a correct title to fix an incorrect one, which is worse than the wart. Disclosed rather than swept.

## Impact

- **Hetzner, in both projects**, by an apply of a reviewed plan. Eight resources are renamed and every labelled resource gains a label. A plan reporting `must be replaced` for any of them stops this change.
- **The live production host**, by a converge: its OS hostname changes for the first time since creation, and the name it *reports* to the tailnet is pinned. The tailnet **machine** name is a different field and is renamed out of band — nothing in this repository can set it. See design.md decision 6.
- **Three things outside this repository that no plan proves**, each an operator step this change's tasks name and sequence: the two Tailscale machine renames, the `PLATFORM_DEPLOY_HOST` Environment secret's value, and the heartbeat checks, whose slug is derived from the server's name.
- **`.github/tests`**, whose 784 tests are this change's largest verification surface and whose literals move with the tree.
