## Why

The platform stack currently has no way to tell whether the host or any service running on it is unhealthy short of noticing manually. `iac-platform-services` already commits to where monitoring will live ("No Dedicated Monitoring Server" — same host, same stack) and `design.md` from `integrate-ansible-host-config` already committed to an external dead-man's-switch as the mitigation for losing observability when the host itself dies, but neither is implemented: there is no metrics collection, no alerting, and no heartbeat. This change builds the first, metrics-based half of that observability story. Log collection and log-content alerting are deliberately deferred to a follow-up change so that alert rules can be tuned against real noise first.

## What Changes

- Add Prometheus, node-exporter, cAdvisor, and postgres-exporter to `platform/docker-compose.yml` as new services, scraped by Prometheus. postgres-exporter connects using a dedicated, restricted-privilege monitoring database role, not the existing Postgres superuser credential; that role is created by a one-time out-of-band operator step (see Impact), not by this change's automation.
- Place Prometheus, Alertmanager, cAdvisor, node-exporter, and Grafana on a new internal-only Docker network, separate from `platform_edge`. `platform_edge` is joinable by any application repository's own Compose file, and these services are not meant to be reachable from application containers.
- Give Postgres a second, private-link-only network shared with nothing but postgres-exporter, so postgres-exporter can reach the shared Postgres instance without ever joining `platform_edge` itself — unlike a network shared with every application, a container's ports are only as exposed as the networks it's actually attached to, so a network with exactly two members exposes nothing to anyone else.
- Configure Prometheus to also scrape Traefik's existing metrics endpoint, giving per-application HTTP error-rate (5xx) visibility for any service routed through it without that service needing its own instrumentation. This requires enabling that endpoint on Traefik's existing service definition, and attaching Traefik to the new internal monitoring network alongside `platform_edge` (its existing network membership for application routing). Because Traefik must remain reachable from `platform_edge`, its metrics endpoint is reachable from application containers too — a narrower, accepted exposure (per-application HTTP status/error-rate counts only, no database or host data, no access to Prometheus/Alertmanager themselves), recorded as a trade-off in `design.md` rather than solved with additional network complexity.
- Add Alertmanager, configured with a single Slack receiver (incoming webhook into the existing Slack workspace), and alert rules for: per-application 5xx rate, container crash-looping/restart/OOM (via cAdvisor, for any container on the host), and host resource pressure (disk/CPU/RAM via node-exporter).
- Add a permanent "Watchdog" alert rule that always fires, routed to periodically ping an external third-party dead-man's-switch/heartbeat service — the first real implementation of the mitigation `design.md` already committed to. Provisioning the third-party account/URL is an out-of-band operator step, not part of this change.
- Add Grafana, reading from Prometheus, for dashboards. Grafana is reachable only over the existing private Tailscale tailnet — not routed through Traefik's public entrypoints, and not attached to `platform_edge` at all — with its admin credential sourced from a secret rather than left at its default.
- Mount the existing but currently-unused `main-data` Hetzner Volume into the platform stack and place Prometheus's and Grafana's persistent data on it, with explicit, bounded retention (not unbounded growth) sized to comfortably fit the volume. Mounting the volume at a fixed host path, with correct persistence and permissions, is new Ansible host-configuration content.
- Prometheus's scrape/alert-rule config, Alertmanager's routing config, and Grafana's datasource/dashboard provisioning are all defined inline in `platform/docker-compose.yml` (via Compose's `configs:`/`content:` mechanism), not as separate files — the existing deploy pipeline transfers only `docker-compose.yml` and `.env` to the host, so any config this change needs on the host has to live inside the one file that pipeline actually delivers.
- All new services are added to the existing `platform/` Compose stack and deployed by the existing `platform-deploy` GitHub Actions pipeline — its forced-command SSH mechanism and fixed `docker-compose.yml`/`.env` archive-member allowlist are unchanged. The workflow's own steps do gain new lines: its `.env`-rendering step gains one line per new secret (same pattern as its existing secrets), and it gains one new step resolving Grafana's tailnet bind address to a literal IP (see below) before rendering `.env`. The volume mount is the one piece of this change outside `platform/` entirely — it's Ansible content (host-configuration scope), consistent with Ansible already owning host-level filesystem concerns.
- New secrets, each sourced the same way existing platform secrets are (a GitHub Actions secret rendered into `.env` at deploy time, or Ansible Vault for the volume mount's own needs), never committed: the Slack incoming webhook URL, the dead-man's-switch heartbeat URL, Grafana's admin credential, and postgres-exporter's database credential. Grafana's Tailscale bind address is *not* a new secret — the deploy job derives a literal tailnet IP from the existing `PLATFORM_DEPLOY_HOST` secret before rendering it into `.env`, since Docker's port-binding needs a literal IP specifically, while that secret may hold either a literal IP or a MagicDNS hostname. It does this by checking the secret's value against a literal-IP pattern first and using it as-is when it matches, resolving via `tailscale ip -4` (on the GitHub Actions runner, already tailnet-joined for this job) only when it doesn't — see design.md's Decisions for why an unconditional resolution call was rejected.

Explicitly out of scope (deferred to a follow-up change):
- Log collection/aggregation (Loki, Promtail/Alloy) and any log-content-based alerting.
- Any per-application opt-in instrumentation (an app exposing its own `/metrics`) — remains each application repository's own future decision.

## Capabilities

### New Capabilities

(none — this extends existing capabilities rather than introducing a new one)

### Modified Capabilities

- `iac-platform-services`: adds concrete requirements for metrics collection, alerting, alert routing/destination, the dead-man's-switch heartbeat, dashboard access, and where monitoring's persistent data lives — turning the existing "No Dedicated Monitoring Server" placement requirement and the Purpose's "eventual monitoring" mention into implemented, testable behavior.
- `iac-host-configuration`: adds a requirement for mounting the platform's dedicated data volume (`main-data`) at a fixed host path, persisted across reboot, with the subdirectories monitoring depends on present and correctly owned before monitoring's containers rely on them.

## Impact

- `platform/docker-compose.yml`: six new services (Prometheus, node-exporter, cAdvisor, postgres-exporter, Alertmanager, Grafana), two new internal-only Docker networks (one for the monitoring services, one private link between Postgres and postgres-exporter), inline `configs:` blocks for Prometheus/Alertmanager/Grafana, plus named volumes/bind mounts. Traefik's and Postgres's existing service definitions each gain one additional network membership; Traefik's also gains its metrics endpoint flag.
- `ansible/`: new content (a new role, or an extension of an existing one) to mount `main-data` at a fixed host path and prepare the subdirectories monitoring's containers bind-mount into.
- `platform/README.md`: status section update once implemented; documents the postgres-exporter role-creation step below.
- Terraform: no resource changes expected — `main-data` volume already exists (`terraform/environments/prod/terraform.tfvars`, `terraform/modules/volume`); this change only starts using it.
- GitHub Actions: new repository/environment secrets for the Slack webhook URL, the dead-man's-switch heartbeat URL, Grafana's admin credential, and postgres-exporter's database credential, each consumed by the existing `platform-deploy` workflow's deploy step.
- Out-of-band operator steps (not automated by this change): creating the Slack incoming webhook in the existing workspace, registering with a third-party dead-man's-switch service, and creating postgres-exporter's dedicated, restricted-privilege database role in the shared Postgres instance. This last step is deliberately kept manual rather than automated: general per-application database/role provisioning inside the shared instance is already tracked as separate, unsolved follow-up work (`platform/README.md`), and this change scopes itself to postgres-exporter's own one-time credential rather than solving that broader problem as a side effect.
