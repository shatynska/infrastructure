## Why

`prune-host-images` ends a completed run with one line: `considered N, removed M`. `considered` is every distinct image identity on the host, not the set the run offered for removal, so the shortfall between the two is dominated by images the keep set correctly protected. A run whose keep set is defective, and whose removals the container runtime therefore blocked, prints `considered N, removed 0` — byte-identical to a healthy run over a host where everything is referenced. The reclamation comment in `app-deploy` calls that shortfall "a signal worth reading"; here there is nothing to read it with.

The gap is not hypothetical, and it is wider than a defective keep set. A removal the runtime rejects is invisible to this script in **both** directions today: the invocation's stderr goes to `/dev/null`, its exit status is swallowed by `|| true`, and the `Deleted:` line the script greps for is simply absent — so the identity is counted in `considered`, not counted in `removed`, and named nowhere. The clearest case is not a defect in the keep set at all. An image carrying no tag but referenced from **two** repositories by digest — an image pulled from a registry and its mirror, which is the digest-pinned class this whole mechanism was built to reach — is removed by identity, and the runtime rejects that with *"must be forced — image is referenced in multiple repositories"*. That image is unreclaimable by this script by construction. It will be offered, rejected and silently left behind every week for the life of the host, and the report will say `removed 0` about it forever. Confirmed against Docker 27 on the `vfs` storage driver this role's Molecule scenario pins, on 2026-09-15.

`docs/backlog.md` entry 5 records this. It was kept out of `prune-unreferenced-host-images-periodically` because it adds a field to a report that change's delta specifies exactly, which is a specification change rather than an implementation detail.

## What Changes

- **A completed run reports a third count: `considered N, removed M, refused R`.** `refused` is the number of distinct image identities for which at least one of this run's own removal invocations was **rejected by the container runtime**. It is anchored to the invocation exactly as `removed` is, and deduplicated by identity exactly as both existing counts are.

- **Each refusal is also named individually**, on standard error, with the identity and the runtime's own message. A count establishes that the run offered something it should not have, or could not remove something it will keep offering; only the message says which of those it was. *"container X is using its referenced image"* is the backstop engaging over a live image and points at the keep set; *"image is referenced in multiple repositories"* points at an image that will never be reclaimed here. Those have different remedies, on the same reasoning the requirement already gives for keeping an absent enumeration distinguishable from an empty one. They are the two causes expected on these hosts rather than the whole set the runtime can produce, which is why the runtime's own text is carried through rather than classified.

- **Nothing about what is removed changes.** The candidate set, the keep set, the by-tag and by-identity removal paths, the pre-removal tag re-check, the refusal to force, the abandon conditions and the run's exit status are all untouched. A refused removal stays a normal outcome and a run carrying refusals still exits zero — the requirement already says so, and a unit that failed because its backstop worked would be reporting the wrong thing.

- **`refused` is read from the removal invocation's exit status, not from its output.** That is what separates a rejection from a removal that succeeded without deleting the image: the multiple-repositories rejection exits non-zero, while `docker image rm` on a tag of an image something else still depends on prints `Untagged:` alone and exits **zero**. `removed` keeps reading `Deleted:` from the output, because the requirement fixes it as "reported the image deleted". Two questions, two reads.

- **The four places that quote the report line are corrected**: three in `docs/bootstrap-a-new-host.md` — §6.4's journal line, and both of §6.5's, the prose sentence about what staging will *not* say and the before/after transition block — and one in the prune script's own comment block, which quotes the line to explain what a swallowed enumeration failure would look like. The role's `README.md` quotes the line nowhere; it gains a section instead, on what a non-zero `refused` means, what each cause calls for, and what the count cannot see.

- **A claim the role's `README.md` has been making is made true.** It says that making a silently-stopped prune alertable "is recorded in `docs/backlog.md`". No such entry exists. This change writes the entry rather than deleting the sentence, since the deferral is real and only its record is missing, and points the sentence at the entry once it does.

- **The `default` Molecule scenario gains a fixture that makes a real refusal happen**, so the new count can be driven non-zero rather than only asserted at zero. One image identity is pushed to two repository paths in the local registry that scenario already runs, and the host is left holding nothing of it; the arrangement step then pulls both references back by digest, leaving an identity with two references and no tag that nothing enumerated references and no container holds. **The fixture is split between the converge and that arrangement deliberately**: built wholly in the converge it would exist before the scenario's first run, every run would report a refusal, and the scenario asserting that a clean run reports none would have no run to assert against. Split, one host yields both — no refusals on the first run, and the fixture's refusal named below the arrangement.

- **The assertion below the arrangement is a named line and a delta, not a literal count**, because that host refuses something else by construction. It builds its fixtures from `alpine:3.19` with the classic builder, nothing references `alpine`, and from the second run onward it is an untagged image with dependent children — which the runtime rejects as *"image has dependent child images"*, a third cause beyond the two above and one `-f` cannot override either. So the post-arrangement run is asserted to carry a refusal line naming the fixture's own identity, and a refused count exactly one greater than the run immediately before the arrangement. That is free evidence that the third cause is real, so it is recorded rather than engineered away.

## Non-Goals

- **Reporting the candidate count.** Naming how many identities the keep set did not reach would give the line a closed arithmetic (`candidates = removed + refused + skipped`), and it was considered on those grounds. It is a second field answering a second question, the backlog entry names one, and `refused` alone is what makes a defective keep set legible; `design.md` Decision 3 records the trade.

- **Reporting tags skipped because they were re-pointed between enumeration and removal.** That is a concurrent deploy behaving exactly as the re-check exists to allow, it is benign by design, and it is not observable in a black-box scenario — the existing suite's own header records why. Counting it would put an unassertable number in the line.

- **Making a refusal fail the run, or retrying it.** Both are forbidden by the requirement this change modifies, and the second would defeat the backstop the count exists to observe.

- **Alerting on a non-zero `refused`.** Nothing scrapes this journal, and making a prune's own output alertable needs node-exporter's textfile collector. The role's README says that deferral is recorded in `docs/backlog.md` and it is not — this change writes the entry, which is the whole of what it does about alerting. It makes the condition legible to an operator who reads the journal; it does not make anything read it for them.

- **Reclaiming a multiply-referenced image.** The image this change makes visible stays on the host. Removing it needs either force — which the requirement forbids, and which would remove the last backstop against a wrong keep set — or removal through each of its digest references, which is a change to what the run removes and wants its own review. Recorded in `docs/backlog.md` by this change rather than folded into it.
