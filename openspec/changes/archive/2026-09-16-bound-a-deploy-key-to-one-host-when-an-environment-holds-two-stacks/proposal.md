## Why

`deploy_apps` lives in `ansible/inventory/group_vars/<environment>.yml`, so an entry there authorises its key on **every host in that environment**. Today each environment holds exactly one stack and therefore one host, so "one key per environment" and "one key per host" are the same sentence and the layout has never been asked to keep them apart. A second tenant ends that: `main-production` and `analytics-production` would be two stacks and two hosts in one environment reading one file, so one application's deploy key — and the `platform` entry's key with it — would authorise a deploy to both.

**The invariant is already normative, in a requirement this change does not modify.** *Deploy Credential Confined to the Gated Job* (`openspec/specs/iac-platform-deploy-pipeline/spec.md`) says it outright: "One stack's key SHALL NOT be able to deploy to another stack's host. Each stack's key is a keypair of its own, whose public half that host authorises and no other host does." Two stacks in one environment under today's layout would breach that requirement, not merely a documented intention — so this change brings the inventory into line with an obligation the specifications already carry, rather than introducing one.

`docs/bootstrap-a-new-host.md` §0.3 states the same thing in as many words, twice: "one leaked private half must deploy to one host", and "they are two keys rather than one because one leaked private half must not be able to deploy to both hosts". The inventory layout does not secure it. `record-how-an-application-is-onboarded` found this while deciding the deploy keys' naming axis, and what that change did was put each key's *name* on the axis its authorisation actually sits on — the honest spelling of the current shape, not a fix for it.

**Nothing reports the gap, which is what decides the timing.** A second tenant would be onboarded by following `docs/onboard-an-application.md`, which produces a key per environment as instructed; both hosts would accept that key and both deploys would succeed, with no error anywhere to say that a second host was authorised. Taken after a second tenant exists, the remedy is a re-key of every application on both hosts. Taken now, while environment, stack and host are one-to-one, it is a layout change in which **no key material moves at all** — the keys this repository already holds satisfy one-key-per-host the moment the file they sit in does.

## What Changes

- **`deploy_apps` moves from `ansible/inventory/group_vars/<environment>.yml` to `ansible/inventory/host_vars/<host>.yml`**, where `<host>` is the Hetzner server name, which is `inventory_hostname` under the `hcloud` plugin and the `name` each stack's `terraform.tfvars` declares. Two files today, `main-production.yml` and `main-staging.yml`, each carrying exactly the entries its own host authorises. **No change to what either role does**: `deploy_user` and `image_prune` read `deploy_apps` from host variables either way, and every Molecule scenario supplies it in its own `converge.yml`. Each role is edited in one respect only, and it is a string a human reads — see the bullet on the two `fail_msg`s below.
- **The static cross-check follows it.** `.github/tests/test_the_platform_stack_deploys_per_stack.py` resolves a stack's deploy-key authorisations through `target_environment` into `group_vars/<environment>.yml`; it will resolve them through that stack's own `terraform.tfvars` `name` into `host_vars/<host>.yml`. The check becomes stricter rather than merely relocated — it is per host where it was per environment — and it stays a static read of committed files.
- **Two requirements change and one is added.** *Each Stack Declares Its Own Pipeline Configuration* (`openspec/specs/iac-cicd-pipeline/spec.md`) names the `group_vars` file of the declared group as where a platform opt-in must be authorised, in one paragraph and two scenarios. *Dynamic Inventory via the hcloud Plugin, One Source per Stack* (`openspec/specs/iac-host-configuration/spec.md`) states which names follow the stack and which follow the environment, and owes the host axis a line now that a file sits on it. The added requirement states the rule itself: a variable belongs in a host's own vars file wherever a second host of a different tenant in the same environment would need a different value or none, and an environment's `group_vars` is for what is true of every host in the environment whatever tenant owns it. **It names its own three unmet placements** — `hardening_ssh_allowed_cidrs`, `hardening_web_allowed_cidrs` and `ops_user_accounts`, which this change does not move — and says it is to be read as unmet in those respects until they do, so the specification is not asserting something of the tree that is false on the day it is archived.
- **The deploy-key naming axis moves with the authorisation.** `docs/naming-conventions.md`'s *The workstation* table, `docs/bootstrap-a-new-host.md` §0.3 and its §0.4 table, and `docs/onboard-an-application.md` all spell the platform and application deploy keys with an environment segment, and say why. The reason is the `group_vars` file, and it stops being true here: both become one key per **stack**, joining the converge key, and the paragraph arguing for the environment is deleted rather than rewritten. Both consuming roles' READMEs follow — `deploy_user`'s for the variable it owns, `image_prune`'s for the sentence describing the same list read from the other side.
- **No key is rotated and no host is touched.** Environment, stack and host are one-to-one today, so each existing keypair already authorises exactly one host; only the file its public half sits in and the name its private half is generated under change. The local key files an operator still holds can be renamed at leisure or not at all, a key being identified by its fingerprint. `.gitignore` needs no new pattern: every stack name ends in its environment word, so `/*-production` and `/*-staging` match the new spellings as they matched the old.
- **Two places name the old file in text a human reads at the moment it matters.** `ansible/playbooks/host-baseline.yml`'s pre-flight commentary names `group_vars` as where a missing `deploy_apps` is corrected; and **both** consuming roles say so in their `deploy_apps` assertion's own `fail_msg` — "Set it in `ansible/inventory/group_vars/<environment>.yml`" — which is the sentence an operator reads **as** the converge refuses. All three are prose rather than logic, and all three follow the file. Two Molecule scenarios assert that same literal, of other inputs this change leaves in place, and are deliberately not touched.
- **`docs/backlog.md`**: entry `bound-a-deploy-key-to-one-host-when-an-environment-holds-two-stacks` is deleted when this change archives, and one entry is added for a finding this change surfaces rather than fixes — that `hardening_ssh_allowed_cidrs` and `hardening_web_allowed_cidrs` mirror **one stack's** `terraform.tfvars` while sitting in an environment's file, and that `ops_user_accounts` grants an interactive login on every host in an environment. Both are the same axis defect without the invariant behind them, and folding them in would put three independent decisions in one change.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `iac-cicd-pipeline`: *Each Stack Declares Its Own Pipeline Configuration* — the paragraph and the two scenarios that name the `group_vars` file of the declared group as where a platform opt-in is authorised, and the sentence listing what a further stack still needs.
- `iac-host-configuration`: *Dynamic Inventory via the hcloud Plugin, One Source per Stack* — the naming paragraph gains the host axis, and the clauses about what a further stack adds and what a stack must carry gain the host vars file. One requirement is **added**, *A Host-Scoped Variable Lives in the Host's Own Vars File*, stating the rule the move implements, naming the three placements it leaves unmet and the backlog entry that resolves them, and stating that a host vars file carries no vaulted content today and that the `--vault-id` label follows the run rather than the file.
