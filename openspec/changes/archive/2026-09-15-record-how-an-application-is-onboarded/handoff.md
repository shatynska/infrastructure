# Handoff: record how an application is onboarded

Opened on 2026-09-14 by `provision-commerce-ops-database-in-the-shared-instance`, at the operator's request, from `docs/backlog.md` entry 51 of the same name. It has no proposal; whoever takes it writes one. Delete entry 51 when this change archives.

## Why

`docs/bootstrap-a-new-host.md` stage 8, *Onboarding an application*, is the whole of what exists, and it sits in a document read front to back once per server. The operator bootstraps a host rarely and adds a service far more often, so the procedure for adding a service belongs in **a document of its own**, readable on its own by someone who is not bootstrapping anything. Entry 51 records the rest of the reasoning; read it in full.

The operator's requirements, stated on 2026-09-14:

- **A separate document**, with stage 8 of the bootstrap document reduced to a pointer to it.
- **Readable**: a forward path someone follows to add one service, not a record of how the procedure came to be.
- **The database step with its explanations kept**, as stage 8.3 now carries them: the block that provisions a role, a database and a password, and the prose beside it. The operator also wants the answer to the questions that block raises the first time it is used, written where the block is, which a session had to give in conversation:
  - **where the password comes from** — generated by `openssl rand -hex 32` inside the pasted block, delivered only over standard input to `gh secret set` and to `psql`, known to nobody afterwards, stored encrypted in the application repository's Environment and as a hash in PostgreSQL;
  - **that it differs per application and per host** — each application gets a role, database and password of its own, even when the secret's name (`SHARED_POSTGRES_PASSWORD`) is reused; staging and production are two independent runs;
  - **that it is never `PLATFORM_POSTGRES_PASSWORD`**, the instance superuser's, which stays in this repository;
  - **what to do when it is lost or leaked** — the same block with `rotate=yes`, picked up on the application's next deploy.

## What bears on it

- **Entry 51's list of what the move has to fix** — the grid of applications × environments and which steps repeat on which axis, stage 8.4's single-target sentences, the key naming and key comments across §0.3 and `docs/naming-conventions.md`, what is reachable before DNS exists and why the host firewall is not what closes those ports, the order that avoids a wasted converge, and what an enumerated-but-undeployed application does to the image prune.
- **Write it from a real onboarding, and say honestly which parts were walked.** `commerce-ops`'s staging onboarding is in progress: its `deploy_apps` entry converged, and its database was provisioned on both hosts by the corrected stage 8.3 recipe — run, failed on a real network fault, re-run and verified. Its application-repository side — a staging deploy job, Compose without a PostgreSQL service, the pre-handover check, the first deploy — had not been walked when this was opened, and is being built in the `commerce-ops` repository. Writing that half before it has been walked is transcription, which is what entry 51 warns against; either take it after, or mark what is unverified and close it when that deploy lands.
- **The operator's documentation preferences** — commands for every step that has one, per operating system where they differ, each with its expected output and how to check it worked, and a plain statement of what is done now versus in a later step; nothing that needs maintaining to stay true — no recommended-order section, no narration of what moved where; reasoning belongs beside the step it explains.

## What it must not undo

- **Extract, do not copy.** One copy of a procedure touching deploy keys, sudoers rules and a database decision; stage 8 keeps a pointer and nothing the new document does not also say.
- **The recipe's safety properties.** Stage 8.3's block is tested by `.github/tests/test_the_shared_instance_has_its_first_database.py`, which reads it from `docs/bootstrap-a-new-host.md` (its `BOOTSTRAP` constant) and requires exactly one fenced block containing `CREATE DATABASE` in that file. Moving the block moves that test's subject: the test has to follow the recipe to its new document, keeping every assertion — the here-document terminating at column 0, the unquoted delimiter, the four log settings, the three secret-name listings and each refusal branch, case-insensitive names, `rotate` assigned in the block. Re-pointing a test at the file its subject moved to is not weakening it; dropping an assertion is. `test_the_bootstrap_documents_static_conventions.py` also reads the bootstrap document's cross-references.
- **The citation rules in `AGENTS.md`** — requirements cited by path and name, changes by name.
- **`provision-commerce-ops-database-in-the-shared-instance` has not archived yet**, and its branch carries edits to stage 8.3's closing `commerce-ops` paragraph and to `docs/backlog.md` entries 10, 19 and 55 that reach `main` only with its archive pull request. Take this change's trunk after that pull request merges, or expect to merge those paragraphs.
