## Context

The `deploy` account (`bootstrap-ansible-host-baseline`) exists today with exactly one capability: an argument-free `sudo` rule triggering `/usr/local/bin/platform-compose-deploy`, used by exactly one key, from exactly one workflow (`platform-deploy.yml`), which reaches it via three sequential SSH operations — `scp` the compose file and `.env`, `ssh` a `chmod`, `ssh` the deploy trigger. That original design deliberately rejected accepting arguments through to `docker compose`, since `docker compose run`/`exec` accept `-v`/`--privileged`/`--user root` on the same invocation line — root-equivalent, just via a different door.

`commerce-ops` (this session's companion change, in its own repository) needs the same kind of access for its own application, and roughly three more application repositories are expected to need it after that. See proposal.md for why a per-application dedicated account was considered and rejected in favor of extending the shared account.

**This design went through two review-driven corrections, both recorded here because they shaped the final shape:**
1. A first draft added new per-application `sudoers` rules without restricting the platform key's own `authorized_keys` entry — since `sudoers` rules apply to the account regardless of which key opened the session, the platform key's pre-existing unrestricted shell would have been able to reach every new application's `sudo` rule. Caught on review.
2. The fix for (1) — a bare `command=` forced command on the platform key — was itself caught as broken on a second review pass: `command=` overrides *every* command sent over that key, and the platform key's real usage sends three different commands in sequence (scp, chmod, sudo trigger), not one. The same flaw was independently present in this change's own new per-application mechanism's first draft (its deploy job was also going to `scp` then separately `ssh` a trigger). Both are fixed the same way: below.

## Goals / Non-Goals

**Goals:**
- Let N applications deploy to this host, each fully isolated from the others' deploy capability, without N dedicated Unix accounts.
- Keep the same invocation-layer safety property the original design established: no session can pass a value to the privileged script that wasn't already fixed in version control ahead of time.
- One SSH connection per deploy, carrying both the content to deploy and the trigger to deploy it — so a per-key forced command can restrict the *entire* session to one fixed script, with nothing left over that a second command could reach.

**Non-Goals:**
- Deciding anything about a specific application's Compose file content, image source, or CI workflow — that's each application repository's own concern (see `commerce-ops`'s `deploy-health-endpoint` change for its side of this).
- Zero-downtime or automatic rollback on a failed deploy. `docker compose up -d --wait` failing loudly (non-zero exit, propagated back through the SSH session to the triggering workflow) is the extent of this change's failure handling — actual rollback tooling is out of scope.

(An earlier draft of this design also listed "migrating `platform/`'s existing deploy mechanism" as a Non-Goal. That's no longer accurate — see Decisions below for why keeping it separate wasn't viable.)

## Decisions

**Content delivery and deploy trigger collapse into one SSH session, for every key — platform included.** Each key's `authorized_keys` entry carries `restrict,command="/usr/local/bin/deploy-receive <app_name>"` (fixed per key, same enumeration principle as before). The connecting client pipes a tar archive containing `docker-compose.yml` and `.env` over stdin in a single `ssh` invocation; `deploy-receive` extracts it, sets permissions, and triggers the privileged deploy — all within that one session, so there is no second command a forced command could fail to anticipate. This is the direct fix for both review findings: it closes the sudo-bleed-through gap the same way the original (broken) bare-forced-command fix intended to, but without breaking multi-step usage, because there no longer is any multi-step usage — everything happens in the one session the forced command governs.

**`restrict`, not just `command=`.** Caught on a further review pass: `command=` alone confines what command a session can run, but says nothing about SSH channel features — a key with only `command=` set can still open port/agent/X11-forwarding channels, letting a leaked key pivot into whatever the host's network can reach even though it can never run anything but the one forced script. `restrict` (OpenSSH ≥ 7.2, available on every currently-supported Ubuntu release this host or CI could plausibly run) disables all of those alongside `command=`'s restriction, closing that gap at zero design cost — it's a key-options addition, not a mechanism change.

**`deploy-receive` extracts an explicit, fixed member list — never a general tar extraction.** `tar -xzf - -C /opt/<app_name> --no-same-owner -- docker-compose.yml .env` names the two expected members explicitly; GNU tar with explicit member arguments extracts only those names, ignoring anything else the archive might contain. This avoids the path-traversal/symlink class of risk a general "extract whatever's in the archive" approach would carry, without needing to hand-write archive validation logic.

**Platform is migrated onto the same generic mechanism — not kept separate.** Once every key needs the "one session, stdin-delivered content, one forced command" shape to be safe at all, maintaining a second, bespoke, platform-only script and forced-command pattern would mean two mechanisms doing the same thing, reviewed and tested twice, drifting independently. `platform-compose-deploy` is retired; the platform key's forced command becomes `/usr/local/bin/deploy-receive platform`, and its sudoers entry becomes `deploy ALL=(root) NOPASSWD: /usr/local/bin/app-deploy platform` — identical in shape to every other application's. `platform/docker-compose.yml` itself, and what `docker compose pull && up -d --wait` does once triggered, are unchanged; only the transport and trigger mechanism change, and they change the same way for everyone. This does touch `platform-deploy.yml` (an existing, live, working workflow) — accepted as necessary, not optional, since the alternative (a bespoke allowlist dispatcher pattern-matching `scp`'s exact wire command for the platform key only) is genuinely more fragile: `scp`'s server-side invocation string varies by OpenSSH client version and protocol (legacy SCP vs. SFTP-based transfer, the default since OpenSSH 9.0), making exact-match dispatching a moving target in a way tar-over-stdin is not.

**Two independent layers still pin the application name.** The SSH-layer forced command fixes which `deploy-receive <app_name>` invocation a given key can ever trigger. Independently, the `sudoers.d` entry fixes the exact `(script, argument)` pair `sudo` will run inside that invocation. An attacker would need to defeat both layers, not one, to trigger a deploy for an application they don't hold a key for.

**The scripts stay thin — no application-name validation logic inside either.** `sudoers` already refuses any application name without a matching rule; `deploy-receive`'s own app name is fixed by which key connected, not read from client input. Neither script re-validates `$1` against an allowlist itself.

**One `sudoers.d` file per application, not one shared file with multiple lines.** Matches the existing convention of small, single-purpose drop-ins; onboarding or removing an application is a single file add/delete.

**Directory permissions mirror `/opt/platform`'s existing shape.** `/opt/<app_name>`, mode `0750`, owned `deploy:deploy`.

**GHCR pull authentication: one shared, read-only, host-level credential — not one per application.** Reaching the host and being able to pull the image it's told to run are two different things, and nothing previously addressed the second. GHCR packages default to private, and `docker compose pull` (run as root, inside `app-deploy`) needs a credential in root's Docker config to succeed against one. Unlike the deploy keys — which must stay per-application, since each one's whole purpose is bounding what it can trigger — a pull credential is read-only and carries no equivalent isolation concern: every application's image already lives in the same GitHub organization's package registry, and a credential that can only ever read packages can't be used to deploy, escalate, or affect any application's running state. One `read:packages`-scoped token, `docker login`'d once as root during host configuration, covers every application.

## Risks / Trade-offs

- [Touching `platform-deploy.yml`, a live, working pipeline] → Mitigated by the change being narrowly scoped to its file-delivery steps (three SSH operations collapsed to one `tar | ssh` pipe); `platform/docker-compose.yml` and the `docker compose pull && up -d --wait` behavior it triggers are untouched. Verified by re-running the existing pipeline post-change (tasks.md rollout section) before considering this change complete.
- [The workflow-file merge and the key-restricting Ansible run are two independent actions with no automatic coordination — doing them at unrelated times leaves a window where the workflow and the key are mismatched] → Caught on review; mitigated by treating them as one coordinated maintenance window (see Migration Plan below and tasks.md's Rollout section), not two independently-timed changes.
- [`command=` alone leaves SSH forwarding channels open on a leaked key] → Caught on review; mitigated by pairing every forced command with `restrict` (see Decisions above), which every `authorized_keys` entry this change creates uses from the start.
- [`deploy-receive` runs as the unprivileged `deploy` user before escalating via `sudo` — a bug in its own extraction logic is a smaller blast radius than a bug in a root-run script, but still runs with whatever `deploy` can already do] → No change from the account's existing content-layer risk (below); `deploy-receive` only ever writes into the directory `deploy` already owns.
- [Content-layer escalation: an application's key can write a hostile Compose file into its own `/opt/<app_name>` and trigger `docker compose up` on it with root privilege] → Same accepted trust boundary the original `deploy` account design already documented for `/opt/platform`, now uniformly true for every application including platform itself, not a new category of risk. Containment is unchanged: whatever gates that application's own CI from pushing to its deploy branch is what actually contains this.
- [A compromised application key can only ever affect its own `/opt/<app_name>`, but the `deploy` account itself is shared] → Mitigated by every capability continuing to route through named, enumerated `sudoers` rules; `deploy` is not, and does not become, a member of the `docker` group.
- [Sudoers file sprawl as more applications are added] → Accepted (one file per app) as the simpler alternative to contention on a shared file.
- [A single shared GHCR pull token, if leaked, could be used to read every application's private package] → Accepted: the token is read-only (`read:packages` only), so a leak exposes container images, not the ability to push, deploy, or affect host state.

## Migration Plan

For every application other than platform, this is new infrastructure with no prior state. Platform's migration needs actual sequencing, because the moment the platform key's `authorized_keys` entry becomes forced-command-restricted, `platform-deploy.yml`'s *old* three-step (`scp`/`chmod`/`sudo`) deploy job stops working — a forced command overrides every command sent over that key, not just the first. Caught on review: changing the workflow file and changing the key are two independent actions (a GitHub merge and an Ansible run) with no automatic coordination between them, so doing them at unrelated times leaves a window where either the old workflow meets the new key restriction, or the new workflow meets the old, unrestricted key — either fails or behaves unpredictably.

The sequencing that avoids this: merge `platform-deploy.yml`'s rewrite first — inert on its own, since the workflow only triggers on `platform/**` path changes and the workflow file itself lives outside that path. Then, treating the rest as one coordinated maintenance window (no `platform/**` merge in between), run the Ansible playbook that restricts the platform key and provisions `deploy-receive`, and immediately validate with a real or dummy `platform/**` change. Only once that validation passes is `platform-compose-deploy` and its old sudoers entry actually deleted (a separate, later playbook change) — until then it sits unreachable (the restricted key can no longer invoke it directly) but present, so if validation fails, rollback is reverting the platform key's `authorized_keys` entry to unrestricted and reverting the workflow file — both cheap, both fully available for as long as neither has been deleted. See tasks.md's Rollout section for the concrete step ordering.

Rollback for any single non-platform application is unaffected by any of this: deleting its `sudoers.d` file, `authorized_keys` line, and `/opt/<app_name>` directory, with nothing else on the host touched by adding or removing one.
