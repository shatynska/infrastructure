## Context

See proposal.md - Why. `deploy_user` already reads `deploy_apps` and gives every entry a `/opt/<name>` directory, a `restrict,command="/usr/local/bin/deploy-receive <name>"` `authorized_keys` line and a `/etc/sudoers.d/app-deploy-<name>` rule — see `ansible/roles/deploy_user/README.md`. Production has carried a `commerce-ops` entry since `add-per-app-deploy-keys`, so this change has a worked shape to copy on the same axis it copies along: another environment, not another mechanism.

The one thing it is not is a copy of production's *credential*, and the reason is in the file it edits: `deploy_apps` entries are per environment so that one leaked private half deploys to one host.

## Goals / Non-Goals

**Goals:**
- Authorise a `commerce-ops` deploy on the staging host, with a keypair that reaches staging and nothing else.
- Leave every prose statement this change falsifies, or finds already false, saying something true: `staging.yml`'s "`commerce-ops` is deliberately absent" and the prune note beside it, `docs/backlog.md` entry 17's "staging has the platform stack and no application" and entry 51's claim that an application is testable over the tailnet with a `Host:` header, and `docs/bootstrap-a-new-host.md` §0.3's "one deploy key per application" with the paragraph above the table and the sentence in §0.4 that point at it. The count is deliberately not given: it grew in every review round, and a number in this line would be the next thing to go stale.

**Non-Goals:**
- Deploying `commerce-ops`. This change makes the deploy possible; the deploy is run by the application's own repository, which has no staging path yet.
- Provisioning staging's `commerce-ops` database, or automating that provisioning. The decision below explains why both sit in a change of their own.
- Opening staging to the web. That is entry 17, it needs a DNS record, and nothing here requires it. Nor a tailnet-scoped allow for port 80, which would be a `hardening` role change with scenarios of its own — see the observation decision below for why none is needed.
- Generalising the two environments' `deploy_apps` into anything shared. They are two lists of public keys that deliberately differ; the duplication is the isolation.

## Decisions

**A keypair generated for staging alone, not production's `commerce-ops` keypair reused.** The alternative is one keypair per application across environments, which is one secret to distribute instead of two — and makes a leaked private half a deploy to both hosts, which is what per-environment entries exist to prevent. `staging.yml` already states this obligation for `platform`'s own keypair; this follows it. The private half stays on the workstation until the operator stores it in the `commerce-ops` repository, and enters this repository in no form.

**The entry is named `commerce-ops`, matching the last segment of `ghcr.io/<org>/commerce-ops`.** Not a free choice: image reclamation identifies an application's images as `ghcr.io/<any owner>/<name>` for exactly the `name` written here, and a mismatch reclaims nothing, silently and indistinguishably from an application that had nothing to reclaim (stage 8.1 of `docs/bootstrap-a-new-host.md`, and `ansible/roles/deploy_user/README.md`). The name is the same as production's for the same reason, which is not the same reason the keypairs differ.

**No specification deltas, `skip_specs: true`.** What a `deploy_apps` entry does is already a requirement and already implemented; this change adds an input to it. A delta here would restate an existing requirement with one more host named in it, which is the kind of restatement that goes stale the next time a host is added. `schema:` and `created:` stay in the file alongside it — dropping `schema:` produces the same "Change must have at least one delta" failure by another route, which reads as though `skip_specs` did not work.

**The infrastructure entry lands before the application repository is ready, not after.** The converge that creates the host objects is a merge to `main` touching `ansible/**`, so the ordering is forced: an application repository that got there first would wait on this pull request anyway. The cost is a window in which staging authorises an application that has never deployed — one directory, one `authorized_keys` line and one sudoers rule that nothing uses. That is the state `staging.yml` was describing when it declined to enumerate `commerce-ops`, and it is now a brief and intended one rather than an indefinite one.

**The database is a change of its own, and this one authorises without provisioning.** The decision about its shape is taken — the shared instance, not a PostgreSQL container of the application's own, staging's data being rehearsal data whose loss is tolerable — and it is recorded in the opened change rather than acted on here. What separates the two is not size: provisioning the first database inside the shared instance falsifies the stated premise of *Single Shared PostgreSQL Instance, Per-Application Databases* ("because no application has needed one") and brings its SHALL due, so it is a specification delta and the derived tests that follow one. A change whose whole diff is an inventory line and three prose corrections cannot also silently modify a capability. The alternative — provisioning here and recording the fired obligation in `docs/backlog.md` — was rejected on the requirement's own reasoning: it says the obligation and its trigger live in the specification rather than only in a document, "because a document describing a procedure is deleted or rewritten when the procedure changes", and a backlog entry's deletion is what success looks like.

**This change does not depend on that one.** The `deploy_apps` entry converges on its own and is observable on its own; it is the rehearsal that waits for a database, and the rehearsal is not what this change delivers.

**The deploy is observed from the staging host over loopback, not from a tailnet device.** The tempting form — `curl -H "Host: …" http://100.85.219.36/` from any tailnet peer — is dropped by UFW, whose default-deny reaches `tailscale0` and whose only tailnet exceptions are the hard-coded 22 and 3000 in `ansible/roles/hardening/tasks/main.yml`. Two alternatives close that gap and both were rejected: opening `hardening_web_allowed_cidrs` is entry 17 and needs the cloud firewall opened with it, and a tailnet-scoped allow for 80 is a `hardening` change of its own, wanting a Molecule assertion and reaching production as well as staging. Neither is needed, because UFW does not filter loopback and Traefik publishes `80:80` and `443:443` on the host: an SSH session the tailnet already permits gets the same request to the same router. It is `https` with `-k` rather than `http`, because the `web` entrypoint redirects to `websecure` unconditionally and no certificate can issue while 443 is closed — so Traefik answers with its own default self-signed certificate, and `-k` is what accepts it. That is also the whole of why a browser still needs entry 17.

**The falsified comments are rewritten, not deleted.** The paragraph in `staging.yml` carries the reasoning about what an enumerated-but-undeployed application does to the prune, which outlives the absence it was written to explain and is worth knowing before it is read as a fault. Entry 17 carries two things recorded nowhere else — the DNS decision's revisit trigger and the two-layer firewall obligation — and its own text says not to delete it.

## Risks / Trade-offs

- [Risk] The window above: an authorisation nothing uses, on a host reachable only over the tailnet. → Accepted and bounded by the application repository's own work; the forced command binds the key to one invocation and `restrict` denies forwarding and a pty, so the authorisation grants a deploy of `commerce-ops` or nothing.
- [Risk] A merge wakes production's approval gate — `host-converge.yml` matrixes over every stack — and a pending run reads as a stuck pipeline. → It is a no-op converge against an unchanged `production.yml`; someone approves it and it reports `changed=0`.
- [Risk] Staging's weekly prune numbers move once the application deploys. → Expected: the keep set gains that application's referenced tags. The current `considered 8, removed 0` is not a baseline to defend.
- [Risk] **The split moved a guard out of the change that creates the exposure.** This change makes a `commerce-ops` deploy to staging possible; the observation that would catch that deploy bringing a PostgreSQL container of its own sits in `provision-commerce-ops-database-in-the-shared-instance`, which this change declares no dependency on. "The application cannot serve a request until its database exists" does not close the gap — an application that finds no database provisioned brings its own, which is exactly production's shape and what *Single Shared PostgreSQL Instance, Per-Application Databases* forbids. → Closed by ordering the one step this repository still controls: the private half is handed to the `commerce-ops` repository only after that change lands, so the authorisation cannot be exercised before the database it is meant to use exists. Stated in proposal.md's Out of scope, where whoever performs the handover will meet it.
- [Risk] Once the application's router exists on staging, Traefik begins a TLS-ALPN-01 issuance it cannot complete — Let's Encrypt answers that challenge by connecting inbound to 443, which is closed at both layers — and retries on its own schedule, logging failures for as long as that lasts. → Nothing to fix here and nothing that harms the deploy; it ends when entry 17 opens both layers. Recorded in that entry's rewrite so it is not chased as a fault.
- [Risk] No risk to production. Nothing in this change is read by the production host, and `production.yml` is untouched.

## Migration Plan

None beyond the converge the merge triggers. The change is additive to a list and every role reading it is idempotent.

**Reverting it is not symmetric, and that is worth stating rather than assuming.** `deploy_user` renders `/opt/<name>`, the sudoers rule and the `authorized_keys` entry per item of `deploy_apps`, and removes none of them for an item that is gone: the `authorized_key` task leaves `exclusive` at its default so each iteration manages only its own key, and the sudoers files are written one per application with nothing enumerating the directory. So deleting this entry stops the role acting on it and leaves the host authorising the key exactly as before — revocation is an edit on the host, or a rotation of the private half in the application's repository, and neither is a commit here. `docs/backlog.md`'s `revoke-an-application-s-deploy-authorisation` records that gap; it is not this change's to close, and it bears on this change only as the reason not to describe the entry as reversible by deletion.
