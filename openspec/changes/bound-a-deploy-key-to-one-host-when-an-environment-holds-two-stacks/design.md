## Context

See proposal.md for motivation. What shapes the approach is that three axes coincide today and one of them is about to move.

A **stack** is a *(tenant, environment)* pair and owns a Hetzner project. An **environment** is one axis of that pair, and is what an Ansible group names. A **host** is what a stack provisions. This repository has `main-production` and `main-staging`, so stack, environment and host stand in a one-to-one-to-one correspondence and every variable sits correctly under every reading of where it belongs. `rename-the-stacks-and-their-resources` already parted the first two — the stack is `main-production` and its group is `production`, and `iac-host-configuration`'s *Dynamic Inventory via the hcloud Plugin, One Source per Stack* records which names follow which. The third was not parted, because nothing had yet asked what a variable's own axis is.

`deploy_apps` is the variable where that question has an answer with a security invariant behind it. `ansible/roles/deploy_user/` renders, per entry, `/opt/<name>`, `/etc/sudoers.d/app-deploy-<name>` and an `authorized_keys` line carrying a forced command; `ansible/roles/image_prune/` reads the same list to build its keep set. Both consume it as a host variable and neither cares which file supplied it, so the whole of this change is where the value is written and what reads that location back.

Three facts bound the work. `inventory_hostname` under the `hcloud` plugin is the Hetzner server name, which `ansible/inventory/group_vars/all.yml` already relies on when it templates the host's own name as `{{ company }}-{{ inventory_hostname }}`. That name is the `name` each stack's `terraform.tfvars` declares, so it is a committed string a static check can read. And `.github/tests/test_the_platform_stack_deploys_per_stack.py` is the only thing that reads `deploy_apps` out of a committed file, resolving it through `target_environment`.

## Decision 1: `host_vars/<host>.yml`, not a per-stack group and not a per-entry selector

`docs/backlog.md`'s entry named three candidates. Taking them in turn.

**A group per tenant-environment pair.** The pair *is* the stack, so the group would be named `main-production` and `group_vars/main-production.yml` would hold the entries. This contradicts *Dynamic Inventory via the hcloud Plugin, One Source per Stack* head-on rather than amending it — "a source is named for its stack and a group is named for its axis, and neither SHALL be derived from the other" — and it would need a third `keyed_groups` entry composing two labels, on a source where `strict: true` makes a missing label fail the whole parse rather than leave a host ungrouped. That mechanism has already cost this repository a converge: `rename-the-stacks-and-their-resources` lost a race with its own apply against a host carrying `environment` and not yet `tenant`. Adding a composite key over both labels widens exactly that window. And the result is still per **stack**, not per host, so a stack that ever holds two servers reopens the hole this change exists to close.

**A host selector inside each entry.** `deploy_apps` entries would gain a `hosts:` field and the roles would filter on it. This puts the axis in data a role must honour, which means an entry omitting the selector has to mean something — and the only two meanings available are "every host", which is the silent over-authorisation restated one layer down, or "no host", which makes a forgotten field delete an application's deploy path. It is the polarity hazard `terraform/stacks/*/pipeline.yml` already warns about twice in its own comments, reached by a different road. It also needs new Molecule coverage in both consuming roles, where the other two candidates need none, and it leaves two tenants editing one file.

**`host_vars/<host>.yml`, chosen.** It is per host exactly, which is the invariant's own wording rather than a proxy for it. It changes no inventory source: no new label, no new `keyed_groups` entry, no widening of the parse window above. The filename is a string Terraform already commits, so the static check can resolve stack → `terraform.tfvars` `name` → `host_vars/<name>.yml` without deriving anything from a name's shape. And it fails closed at two depths. `.github/tests` refuses a stack whose host vars file is missing at pull-request time; and if one slipped past, `deploy_user`'s own assertion refuses the converge by name rather than authorising nothing quietly.

**That second depth is read off the role rather than assumed**, because the difference matters: *A Role's Absent Required Input Is Reported by Name* (`openspec/specs/iac-host-configuration/spec.md`) permits a role to define an empty value as meaningful, and a role defaulting `deploy_apps` to `[]` would satisfy that requirement while silently de-authorising every deploy key on the host. `ansible/roles/deploy_user/tasks/main.yml` does the opposite: its first task, before anything changes the host, asserts that `deploy_apps` is defined and is a list, and its own comment records that definedness is checked *deliberately* rather than non-emptiness, an empty list meaning "no application may deploy here". `defaults/main.yml` refuses to carry a default and says that adding one would defeat the assertion. `.github/tests/test_ci_configuration.py` already asserts that this role carries that input's assertion, so the guarantee is held by a check rather than by this paragraph. `image_prune`, the other consumer, is built the same way.

What it costs is that the two hosts' entries are no longer written once. Today that costs nothing — the two files already differ, production carrying `platform` and `commerce-ops` and staging its own pair — and where two hosts genuinely should authorise the same application, they are authorising it with two different keys anyway, which is the whole point.

## Decision 2: the filename is the host's name, and its drift fails loudly

`host_vars/main-production.yml` is keyed on a name Terraform owns. Renaming a server in `terraform.tfvars` therefore orphans the file, and it is worth being explicit about what happens then, because the failure mode is the thing this change is trying not to recreate.

At pull-request time the static check compares the stack's declared `name` against the set of committed host vars files and fails naming both, which is the same shape as the existing check that compares a stack's declared group against the set of `group_vars` files. Past that, a converge against a host with no host vars file reaches `deploy_user`'s pre-flight assertion, which refuses by name under *A Role's Absent Required Input Is Reported by Name*. Neither path can produce a host that is authorised for something nobody wrote down — the failure is always "no entries", never "the wrong entries".

That is a stronger guarantee than the group_vars layout gave, where a renamed stack whose group was unchanged kept reading the same file and would have kept authorising the same keys.

## Decision 3: only `deploy_apps` moves, and the residue is recorded rather than folded in

`ansible/inventory/group_vars/<environment>.yml` holds more than one variable whose axis is questionable once two tenants share an environment.

- `hardening_ssh_allowed_cidrs` and `hardening_web_allowed_cidrs` mirror **one stack's** `terraform.tfvars` exactly, and the mirror obligation in `ansible/roles/hardening/README.md` is per stack by nature. Two tenants' production stacks may open different ports to different places.
- `ops_user_accounts` grants an interactive, `docker`-group login. An operator of one tenant's host is not thereby an operator of another's.
- `ansible_user`, `platform_data_volume_subdirs`, `platform_data_volume_superseded_mount_paths` and `ghcr_pull_username` are genuinely environment-wide, and two of them are byte-identical across both files today for stated reasons.
- `image_prune_heartbeat_ping_key` is a **project** ping key rather than a per-check key, as `group_vars/production.yml`'s own comment records, so sharing it across an environment's hosts is what it is for.
- `ghcr_pull_token` is a read credential for a registry both hosts pull the same images from.

Only `deploy_apps` carries an invariant this repository has written down and asserted elsewhere, and only `deploy_apps` is enumerated by a required status check. The first two bullets are the same axis defect without that backing, and each needs a decision of its own — whether a per-stack CIDR pair defeats the point of an environment-wide hardening baseline, and whether operator access is per environment or per tenant. Folding three independent decisions into one change makes the review of all three worse. They go to `docs/backlog.md` as one entry, `put-the-remaining-host-scoped-variables-on-the-host-axis`.

**The added requirement names them itself, rather than leaving the deferral to that entry alone.** A general SHALL that the committed tree knowingly breaks in three places, with nothing recording the exception, is a rule read as advisory the first time someone notices — and `openspec validate` cannot see a variable's placement, so nothing mechanical would catch it. So the requirement states the three, says it is to be read as unmet in those respects, and says the paragraph is replaced when they move and not before. That is the form *Single Shared PostgreSQL Instance, Per-Application Databases* (`openspec/specs/iac-platform-services/spec.md`) already uses for its own outstanding obligation, and the reason is the same one it gives: a backlog entry is deleted when its change is archived, so an obligation recorded only there does not survive its own resolution path.

## Decision 4: the deploy keys' naming axis moves to the stack, and no key is rotated

`record-how-an-application-is-onboarded` argued the naming axis from the authorisation: "what a deploy key authorises is an entry in `ansible/inventory/group_vars/<environment>.yml`", so the name carries the environment, and "a name spelling the stack would claim a narrower blast radius than the key has". That argument is correct and its premise is what this change falsifies. Once the entry sits in a host's own file, the narrower claim is the true one.

So both deploy keys become one per **stack**, joining the converge key, which `docs/naming-conventions.md` currently has to explain as the odd one out. The paragraph doing that explaining shrinks rather than grows: all three per-target keys end up on one axis, and the *The workstation* table's two "one per environment" labels become "one per stack". The platform key's stored half is already per stack, in that stack's own GitHub Environment as `PLATFORM_DEPLOY_SSH_KEY`, so storage and authorisation stop disagreeing.

**Nothing is re-keyed.** Environment, stack and host are one-to-one, so `~/.ssh/<company>-platform-production`'s keypair already authorises exactly one host; it becomes `<company>-platform-main-production` by a rename, or by nothing at all, since a key is identified by its fingerprint and not by its filename. The public halves committed here do not change by a byte — the task list verifies that by fingerprint rather than by inspection. `.gitignore` needs no new pattern because every stack name ends in its environment word, so `/*-production` and `/*-staging` match `<company>-platform-main-production` exactly as they matched `<company>-platform-production`; `.github/tests/test_the_bootstrap_documents_static_conventions.py` asserts that coverage and will confirm it rather than needing to be taught.

## Decision 5: the cross-check resolves through Terraform, not through the group

`.github/tests/test_the_platform_stack_deploys_per_stack.py` implements *Each Stack Declares Its Own Pipeline Configuration*'s obligation that a stack opting in to the platform deploy must also authorise it on its host. It resolves stack → `pipeline.yml` `target_environment` → `group_vars/<environment>.yml` → `deploy_apps`.

The new path is stack → `terraform.tfvars` `name` → `host_vars/<name>.yml` → `deploy_apps`. Both ends stay static reads of committed files, which is the constraint `.github/tests` holds itself to.

The check gets stricter in a way worth naming. Under the old path, two stacks in one environment resolved to one file, so one `platform` entry satisfied both stacks' opt-ins — the required check would have passed on exactly the tree this change exists to prevent. Under the new path each stack resolves to its own file, so each opt-in is answered by its own host's authorisation or fails. The requirement's text did not change meaning; the file it named stopped being able to express it.

## Decision 6: now rather than at the second tenant

The entry this change comes from says "take this before a second tenant exists rather than after, since afterwards the remedy is a re-key rather than a layout", and the timing is the substantive part of the decision rather than a scheduling note.

Before: no key material moves, no host is touched, no deploy is interrupted, and the whole change is a file move, a check's resolution path and the prose that explains both. After: every application on every host in the shared environment holds a key that authorises two hosts, each private half is in a different repository's Environment secrets, and correcting it means generating, distributing and swapping each one while deploys continue.

There is a cheaper thing that was considered and rejected: leaving the layout alone and adding a check that fails the pull request which adds a second stack to an existing environment. It would preserve the deadline — that pull request lands before that tenant's keys are generated — but it is work that the real fix deletes, and it leaves the repository in a state where a requirement's own text is true only by an accident of how many tenants exist.

## Open question for implementation

**Whether Ansible loads `host_vars/` adjacent to a plugin inventory source is to be established by running it, not by reading this.** `group_vars/` is loaded from beside `ansible/inventory/*.hcloud.yml` today and the same adjacency rule governs `host_vars/`, but this repository has been wrong before about a plugin's behaviour read rather than measured — `main-production.hcloud.yml`'s own comments record two such corrections, one of them a claim about `strict:` that was measured against the wrong plugin. `tasks.md` carries the measurement as a task with a stated command, and its result is the gate on everything downstream of it.

**What a negative result means, stated now rather than improvised then.** If `host_vars/` is not loaded from beside the source, the layout decision stands and only its mechanism changes: the candidates are declaring the inventory as a *directory* containing both the source and its vars directories, or naming the vars path explicitly in `ansible.cfg`. Either is a change to how every run resolves inventory, which is larger than this change's scope and touches `Dynamic Inventory via the hcloud Plugin, One Source per Stack` in ways these deltas do not. So a negative result stops the change at `plan` and is raised, rather than being worked around inside it — it is not a licence to fall back on a per-entry host selector, which Decision 1 rejected on its own merits and which a mechanism failure does not make better.

**A second fact of the same kind is measured beside it**: that the `name` each stack's `terraform.tfvars` declares *is* the Hetzner server name, rather than an input the `server` module composes one from. Decisions 2 and 5 both resolve a filename through that string, and an assertion built on a composition rule that happens to be the identity on two stacks is the failure Decision 1 rejects the composite-group candidate for. Task 1.1 reads both halves off one run.
