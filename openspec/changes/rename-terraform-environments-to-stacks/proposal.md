## Why

`terraform/environments/` names an axis that has stopped being the organising one. The unit this pipeline discovers, plans, applies, drift-checks and converges is **one Terraform root module: one state, one Hetzner project, one blast radius** — and `docs/naming-conventions.md` calls that a **stack**. A stack is a *(tenant, environment)* pair, so environment survives as a field inside the stack's name rather than as the thing the folder is divided by. The case that breaks the present word is a tenant with no staging: under `environments/` it reads as a missing directory, under `stacks/` it is simply a tenant with one stack.

This is `docs/change-queue.md` entry 61, the **first of four** that deliver the scheme in `docs/naming-conventions.md`; entries 62, 63 and 64 are blocked behind it. It goes first so that entry 62 does not rewrite the same specification text twice.

**Renaming the folder without the vocabulary would be worse than doing nothing.** A directory called `stacks/` iterated by a shell variable called `environments_root` and a matrix key called `environment` is a scheme that contradicts itself inside one file, and a reader has no way to tell which word is load-bearing. The path and the vocabulary move together or neither moves.

**No live effect.** Terraform state is keyed by the HCP workspace named in each `cloud` block, not by the directory's path, so nothing in Hetzner or HCP observes this change. No environment's *value* is renamed either: the directories stay `prod` and `staging`, and no label, Hetzner resource, GitHub Environment, repository secret or HCP workspace is touched. Those are entries 62 and 63, deliberately separate because their correctness is established by a pull-request plan and by repository settings respectively, and this change's is established by a test suite.

## What Changes

- **`terraform/environments/` becomes `terraform/stacks/`.** `git mv` of both directories; no file inside either one changes as a consequence of the move itself.
- **The discovery vocabulary follows the path.** In all four discovery bodies — the one `pr-validation.yml`, `apply.yml` and `drift.yml` share, and `host-converge.yml`'s deliberately different fourth — `environments_root` becomes `stacks_root`. The matrix key `environment` becomes `stack`, so every `matrix.environment.*` becomes `matrix.stack.*`; the `discover`, `affected` and `planned` job outputs named `environments` become `stacks`; the `ENVIRONMENTS`, `ENVIRONMENT_NAME` and `REQUESTED_ENVIRONMENT` shell variables become `STACKS`, `STACK_NAME` and `REQUESTED_STACK`; and `host-converge.yml`'s `workflow_dispatch` input `environment` becomes `stack`. `TARGET_ENVIRONMENT` is the one that does **not** move — see below.
- **The prose around that mechanism follows it too** — step names, `::error::` messages, job summary headings and the block comments that explain the bodies. A message reading *"Environment discovery found no `terraform/stacks/` directory"* would name the mechanism by a word the mechanism no longer uses, which is the same defect the bullet above avoids, one layer out.
- **`.github/tests` follows.** The suite asserts these literals, and it locates the shared discovery body by the `terraform/environments` literal that body contains rather than by its step name, so it changes in the same commit or the locator stops finding what it executes. Its 601 tests are the largest part of this change's verification; design.md decision 6 is the authority on the rest.
- **`.github/dependabot.yml`**, whose two Terraform directories are absolute paths, and the `terraform/environments/**` path filter inside `pr-validation.yml`'s changed-files step.
- **Requirement text in six specifications**, twenty-one requirements in total, plus three capability `## Purpose` lines — the path where it occurs, and the word wherever it names the unit the pipeline iterates over, which is a wider set than the requirements carrying the path and reaches two capabilities that name no path at all. All nine capabilities were read to select them. See design.md decision 2.
- **Documentation**: `README.md`, `docs/bootstrap-a-new-host.md`, `AGENTS.md`, `.envrc.example`, `ansible/.envrc.example`, the two Ansible inventory sources and their `group_vars`, three Ansible role files that cite the path, `docs/deferred-work.md` and `docs/change-queue.md`.

## What Does Not Change, and Why Each One Is Named

The boundary is where this change is easiest to get wrong, so each case is stated rather than left to be inferred:

- **The environment values `prod` and `staging`.** The directories keep their names. Entry 62 renames them to `main-production` and `main-staging` together with the Hetzner resources, the labels, the inventory sources and the `group_vars`, because that change's correctness rests on a pull-request plan proving Hetzner renames in place — evidence this change neither has nor needs.
- **`pipeline.yml`'s `github_environment` field, every `environment:` job key, and every GitHub Environment name.** These name GitHub Environments, which is what GitHub calls them. Renaming them here would be renaming a different thing that happens to share a word.
- **The Terraform `environment` label and variable, and the Ansible groups derived from it.** The environment axis is still an axis; `docs/naming-conventions.md` keeps it. Entry 62 spells its values in full.
- **`target_environment`, `TARGET_ENVIRONMENT` and the `--vault-id` label.** These name the Ansible group a converge play targets, and they are governed by *Host Configuration Names the Environment It Targets* (`openspec/specs/iac-host-configuration/spec.md`), with consumers in `ansible/playbooks/host-baseline.yml`, `.ansible-lint`, `.pre-commit-config.yaml` and `docs/bootstrap-a-new-host.md`. They equal the stack name today only because the two coincide at one tenant; after entry 62 the group is `production` while the stack is `main-production`, so re-deriving them is that entry's work. The assignment becomes `TARGET_ENVIRONMENT: ${{ matrix.stack.name }}` and carries a comment saying why the two names differ. `iac-host-configuration` is untouched in full for the same reason.
- **The names of the twenty-one modified requirements, and the names of their scenarios.** Three requirements carry *Environment* in their title, and renaming a requirement is a `RENAMED` delta. `apply-host-configuration-through-a-gated-workflow` is in `ship` with an unarchived delta that `MODIFIED`s one of them — *Each Environment Declares Its Own Pipeline Configuration* — so a rename here produces, on whichever of the two archives second, a delta naming a requirement that no longer exists. Scenario names are barred by the tool rather than by judgment: a `MODIFIED` requirement replaces its block whole, so `openspec validate` reads a renamed scenario as a dropped one and refuses the change. Scenario **bodies** change freely and do. Both are deferred to entry 62, which rewrites this text anyway and which that change will have archived before. Recorded there rather than only here.
- **`.github/tests` module filenames and test-method names.** `test_environment_agnostic_pipeline.py` and its siblings assert nothing about the word in their own names, and renaming them would churn several hundred test identifiers without changing what a single one checks. Disclosed rather than done; also recorded against entry 62.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

Twenty-one requirements and three capability `## Purpose` lines, across six of the nine capabilities. The selection rule is design.md decision 2's — *the word names the unit the pipeline iterates over* — which is wider than *the text contains the path*, and the difference is the nine marked below. The three capabilities left untouched are named at the end.

- `iac-repo-foundations`: **two requirements**, plus the capability's `## Purpose` ("environment/module folder structure"). *Environment and Module Folder Structure* prescribes the directory layout itself and is the requirement this change is most directly about; it also gains one sentence defining what a stack is, because after this change the specifications use a word none of them defines, and the requirement that prescribes the directory is where that definition belongs. *Version Control Excludes State and Secrets* names `terraform/environments/<env>/terraform.tfvars` in its tracked/ignored table and plans against `terraform/environments/prod/` in a scenario.
- `iac-state-management`: **four requirements**, plus the capability's `## Purpose` ("each environment operates against"). *Remote State Backend* names the directory in two scenarios; *State Locking* names it in one. **Neither of the next two names the path**: *Workspace Execution Mode Set to Local* obliges the setting on "every environment's workspace" and on adding one, and *Each Environment Has a Dedicated Hetzner Cloud Project* states the project boundary in the exact terms this change's own stack definition uses. *Remote State Backend*'s workspace-name derivation moves from `infrastructure-<environment>` to `infrastructure-<stack>`; the two coincide today and diverge at entry 62, and entry 63 is what changes the workspace names themselves.
- `iac-safety-hardening`: **five requirements.** *Provider-Level Deletion Protection*, *Data Durability for Stateful Resources* and *Consistent Resource Labeling* each name `terraform/environments/prod/` in prose or a scenario; the last keeps its `environment` label anchored to the environment axis rather than to the directory, because `docs/naming-conventions.md` separates the two at entry 62. *Write Credentials Confined to the Gated Pipeline* names the directory in three scenarios. **The fifth names no path**: *Automated Dependency Updates* obliges that "adding a Terraform module or environment SHALL include adding it here", where *here* is the Dependabot directory list this change edits.
- `iac-cicd-pipeline`: **eight requirements**, which is the count `docs/change-queue.md` entry 61 estimated at "roughly ten". *Pull Request Validation Checks* obliges `terraform validate` and `tflint` to discover directories under the root rather than enumerate them. *Pull Request Plan Visibility* and *Gated Production Apply Applies the Reviewed Plan* state the path rule that maps a changed file to the units it affects, and are the two requirements where the word names the iterated unit throughout. *Each Environment Declares Its Own Pipeline Configuration* obliges every directory under the root to carry `pipeline.yml`. **Four name no path** and are the ones a path-driven sweep misses: *Credential Scoping by Privilege* ("this split SHALL hold per environment"), *Destroy Policy Gate* ("a per-environment policy, declared by the environment itself"), *Serialized Terraform Runs* ("a `concurrency` group per environment … derived from the environment's own identity") and *Scheduled Drift Detection* ("`terraform plan` against every environment") — the last being the one that would have left `drift.yml` iterating `matrix.stack` under a requirement still saying environment.
- `iac-server-lifecycle`: **one requirement**, and `iac-data-volumes`: **one requirement** plus that capability's `## Purpose`. **Neither names the path.** *Conditional Prod Server Creation* obliges that "the prod environment SHALL expose a boolean variable" and that configuration "remain declared in the environment's variables and non-secret tfvars"; *Conditional Prod Volume Creation* says the same of the volume. The file they describe is `terraform/stacks/prod/terraform.tfvars` — the one *Version Control Excludes State and Secrets* now calls stack configuration — so leaving them would describe a single file in two vocabularies across three capabilities.

Three capabilities are deliberately untouched. `iac-host-configuration` names the environment a play targets, which is the axis rather than the unit — the same reason `target_environment` stays. `iac-platform-services` and `iac-platform-deploy-pipeline` are about the shared Compose stack on a host, a different thing that already owns the word *stack*; the definition this change adds says so explicitly, so the two senses are distinguished rather than conflated.

## Impact

- `terraform/environments/prod/` and `terraform/environments/staging/` move to `terraform/stacks/`. **`git mv` moves tracked files only**: `terraform/environments/prod/` also holds an untracked, gitignored `.terraform/`, and the repository-root `.envrc` is prod's local read-only-token file. After the move `terraform init` must be re-run in both moved directories and any local `direnv` arrangement re-pointed by hand. Neither is in the diff, so neither is visible to review — recorded in `tasks.md` where an operator resuming this tree will read it.
- `.github/workflows/pr-validation.yml`, `apply.yml`, `drift.yml`, `host-converge.yml`.
- `.github/tests/` — the asserted literals and the scratch trees the discovery tests build, across six of its eight modules.
- `.github/dependabot.yml`.
- `openspec/specs/` — six capabilities, twenty-one requirements and three `## Purpose` lines, through this change's deltas.
- `openspec/changes/apply-host-configuration-through-a-gated-workflow/specs/iac-cicd-pipeline/spec.md` — that change's own unarchived delta `MODIFIED`s a requirement this change also modifies, so the two bodies are made identical and the order of archive stops mattering; its `ADDED` requirement, which governs `host-converge.yml`, is swept on the same reasoning. The sweep and the directory move travel in one pull request, so both archive orders are consistent; what that requires is that this change never merge in its plan-and-tests state. See design.md decision 4 and tasks.md 7.3.
- Documentation and `direnv` examples, listed under *What Changes*.
- **One-time cosmetic effect on open pull requests.** `pr-validation.yml` finds its existing plan comment by `body-includes` on a heading carrying the path. A pull request already carrying a comment under the old heading gets a second comment rather than an edit, once. Nothing is lost and the next run is clean.
- **An open drift issue is orphaned, and this one does not self-correct.** `drift.yml` builds its issue title as `Terraform drift detected: terraform/environments/<name>` and matches on the **whole** title — deliberately, since a tokenised search would let one stack's drift reach another's issue. After the rename no open issue matches, so a drifting stack opens a second issue under the new title and no later clean run ever closes the first. It stays open, naming a path that no longer exists, which is the muted-report failure the requirement's own prose warns about. Task 9.1a closes any such issue by hand at merge.
- `docs/change-queue.md` — entry 61 deleted, and entries 60, 62, 63 and 64 updated.
- No infrastructure change, no credential change, no repository-settings change.
- Unblocks `docs/change-queue.md` entries 62, 63 and 64.
