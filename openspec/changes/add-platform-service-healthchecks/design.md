## Context

See `proposal.md` for the incident this change fixes, and for the scope expansion (Traefik/Postgres folded in) discovered during implementation. Relevant existing constraints:

- `app-deploy` (on the host, provisioned by `iac-host-configuration`'s forced-command deploy account) runs `docker compose up -d --wait`, which — per `deploy-platform-compose-stack`'s design record — is this project's already-chosen mechanism for failing the deploy job on a partial deploy. No separate post-deploy health check exists or is being added; this change makes that existing mechanism actually work for the whole stack.
- Compose's `--wait` behavior: a service with a defined `healthcheck:` is waited on until it reports `healthy` (or the wait times out, failing the command); a service with none is only waited on until it reaches `running` state, which is what let the crash-looping Grafana container in the incident report as "Healthy" in the deploy log.
- **Corrected understanding of that "running state" fallback**, established by live testing during this change's implementation, not assumed: it is not a reliable safety net for a service under `restart: unless-stopped` (which every service in this stack uses). Deliberately breaking Traefik's entrypoint so it crashes immediately and reproducing twice: `docker compose up -d --wait` reported success (exit 0, Traefik listed as "Healthy") while Traefik had already auto-restarted 6-8 times. Compose's wait is satisfied by the container reaching `running` even transiently, which a crash-restart cycle provides on every cycle. This is why Traefik and Postgres are folded into this change's scope rather than left to that fallback.
- The `deploy` account's SSH key is restricted to the forced command `deploy-receive platform` (`iac-host-configuration`'s "Restricted Deploy Account Supports Per-Application Forced-Command Deploys" requirement) — nothing in this change touches that restriction or needs to.

## Goals / Non-Goals

**Goals:**
- Make a broken deploy of any service in the shared stack fail loudly, for any cause that stops that service's own HTTP/readiness layer from becoming reachable and ready — which is what the incident's cause (and most realistic startup failures: bad config, permission errors, missing dependencies at the process level) actually looks like — using the mechanism this project already relies on.
- The one class of failure this goal does **not** cover: a service whose HTTP server comes up fine but which cannot do its actual job for an external reason (postgres-exporter reachable but unable to authenticate to Postgres is the concrete case here — see the Decisions table). That gap is real, pre-existing, and out of scope for this change; it stays covered by `MetricsTargetDown` instead.

**Non-Goals:**
- Any new pre-flight check, SSH capability, or automation of the Ansible-run step. Ansible remains manually operator-run, unchanged.
- Retrying or auto-remediating a failed deploy — failing loudly and visibly is the whole goal; recovery stays a human action, as it already is for any other deploy failure.

## Decisions

**One `healthcheck:` per service, each hitting that service's own real readiness signal, not a generic "is the process alive" check — now covering all eight services, not just the six `add-platform-monitoring` introduced.**

| Service | Healthcheck |
|---|---|
| Traefik | `traefik healthcheck --ping` — Traefik's own built-in healthcheck subcommand, calling its `/ping` endpoint. Requires `--ping=true` added to Traefik's `command:` (disabled by default); uses Traefik's implicit internal entrypoint (default port 8080, unpublished — same trust boundary already accepted for the existing `metrics` entrypoint, reachable only via Docker networks, never the host). Verified live: `--ping.entrypoint`/`--entrypoints.<name>.address` flags must otherwise be repeated in the healthcheck invocation itself (it's a fresh CLI parse, not a call into the running process's already-parsed config) — using the default entrypoint name avoids that repetition entirely, keeping the healthcheck command simple. |
| Postgres | `pg_isready -U $POSTGRES_USER` (via `CMD-SHELL` for the env var) — the official `postgres` image ships `pg_isready` for exactly this use; confirmed it reports "accepting connections" once ready and would fail otherwise. |
| Prometheus | `wget --spider -q http://localhost:9090/-/ready` — Prometheus's own documented readiness endpoint (distinct from `/-/healthy`, which reports healthy before the TSDB and rule manager are actually ready to serve/evaluate). |
| Alertmanager | `wget --spider -q http://localhost:9093/-/ready` — same rationale: Alertmanager's own readiness endpoint, not just "is the process up." |
| Grafana | `wget --spider -q http://localhost:3000/api/health` — Grafana's documented health endpoint; this is exactly the check that would have caught the incident, since Grafana fails to reach a ready state (and this endpoint reflects that) when its data directory isn't writable. |
| node-exporter | `wget --spider -q http://localhost:9100/metrics` — no dedicated readiness endpoint exists; successfully serving its metrics page is the closest real signal that it's doing its job, not just that the binary launched. |
| cAdvisor | `wget --spider -q http://localhost:8080/healthz` — cAdvisor's own documented health endpoint. Confirmed working against v0.60.5 (this stack's current version, bumped by `fix-cadvisor-containerd-snapshotter`), not just the version this change was originally drafted against. |
| postgres-exporter | `wget --spider -q http://localhost:9187/metrics` — same reasoning as node-exporter: no dedicated readiness endpoint, so this only confirms the exporter's own HTTP server is up, not that it can actually reach or query Postgres. `postgres_exporter`'s `/metrics` handler returns HTTP 200 regardless of database connectivity (a bad DSN or missing role shows up as `pg_up 0` in the metrics body, not as a failed HTTP response), so this healthcheck deliberately does **not** claim to catch that class of failure — that's already caught by `add-platform-monitoring`'s separate `MetricsTargetDown` alert (`up == 0`), a different, alerting-based detection path, not this deploy-time one. Confirmed live: pointed at a real Postgres with no `pgexporter` role, the exporter logs a password-authentication failure and serves `pg_up 0`, yet its own healthcheck still reports `healthy` — the gap is real, not a stale assumption. |

`wget` (or the image's own dedicated tool, for Traefik/Postgres) is used throughout — present in each image already — rather than adding a new dependency to any image. Confirmed live against every one of the eight currently-running production images, not just assumed from documentation.

**Alternative considered and rejected: a single pre-flight SSH check (e.g. `findmnt /mnt/main-data`) run from the GitHub Actions job before delivering the Compose file.** This was the first fix considered, and rejected: it would require either widening the `deploy` account's forced-command restriction (a real, deliberate security boundary this project does not lightly touch) or adding a second SSH credential with broader command execution rights, and it would only catch this one specific cause (the volume not being mounted) rather than the general class of "a service didn't actually come up" failures. The healthcheck approach catches this incident's cause and every other way a service could fail to become ready, through a mechanism that already exists and needs no new credential or workflow step.

## Risks / Trade-offs

- [Risk] A healthcheck endpoint could itself be flaky or slow to respond under load, causing `--wait` to time out and fail a deploy that was actually fine. → Mitigation: each check hits a lightweight, purpose-built readiness/health endpoint each project documents for exactly this use, not an expensive query; Compose's default healthcheck interval/timeout/retries give a service a reasonable window before being judged unhealthy.
- [Risk] `wget`/`pg_isready`/`traefik healthcheck` availability differs slightly across these images — an assumed-present binary that turns out missing would make the healthcheck itself fail to execute, masking the real signal behind a different error. → Mitigation: every one of the eight healthchecks was run live against the actual running production images (or, for Traefik/Postgres, an identically-tagged local container) before being written into the Compose file, not just assumed from documentation — see task list.
- [Risk] postgres-exporter's healthcheck cannot detect a bad database credential or a missing/dropped `pgexporter` role — `postgres_exporter` serves `/metrics` with HTTP 200 regardless of database connectivity, so the container-level healthcheck stays "healthy" in exactly that failure. → Mitigation: this specific gap is already covered by a different mechanism, `add-platform-monitoring`'s `MetricsTargetDown` alert — slower (alert-based, not deploy-blocking) but real. Not solved here; documented as a known, accepted residual gap rather than silently left unstated.
- [Risk, discovered during implementation, now addressed by this change's expanded scope] The "no healthcheck → wait for running state" fallback does not reliably catch a crash-looping service under `restart: unless-stopped` — see Context. Originally this meant Traefik/Postgres had effectively no real deploy-time crash-loop protection despite the design record's stated intent. → Mitigation: no longer a residual risk for this stack, since every service now has a real healthcheck — but the `iac-platform-deploy-pipeline` spec delta's language for a hypothetical future non-healthchecked service is corrected to state this limitation honestly, rather than repeat the original, now-disproven "reaches running → deploy fails if not" claim as a reliable guarantee.

## Migration Plan

Purely additive to eight existing service definitions; no new service, network, or secret. Traefik's `command:` gains one new flag (`--ping=true`); no other workflow change. Rollback is reverting the eight `healthcheck:` blocks (and Traefik's `--ping` flag). No data or running-state impact — a redeploy after this change picks up the healthchecks the same way any other Compose service definition change is picked up.
