## Why

`docs/naming-conventions.md` records a naming scheme this repository does not yet match, and says which changes bring it there: entries 61, 62, 63 and 64, in that order. Entry 61 renamed the *word* — the Terraform root became `terraform/stacks/` and the unit became a *stack*. Entry 62 renamed the *values this repository owns* — the stack directories, the Hetzner resources and the labels. **This change renames the four things that live outside the repository**, which is everything the scheme names that no commit can move: the two HCP Terraform workspaces, the two GitHub Environments, the two read-only repository secrets and the two Hetzner projects.

**It is separated from entry 62 because nothing here is provable by a plan.** Entry 61 was verified by a test suite; entry 62 by a `terraform plan` showing four in-place updates per stack. Every step here is a click in a web interface whose effect no file in this repository can verify, and folding them into a Terraform change would produce one pull request whose green result meant less than it appeared to. The green pull request this change opens still means less than usual, and the evidence that matters is the five observations at `tasks.md` 9.1 — one per external service, plus the converge that exercises three of the renames at once, plus a plan that establishes the one claim this change could not measure in advance.

**Entry 62 left two commitments pointing here, and they are the reason this is a change rather than a preference.** Each `versions.tf` carries a comment saying its workspace name and its directory name are *deliberately* out of step until this entry — a comment that stops being true the moment this lands and is deleted by it. And *Remote State Backend* (`openspec/specs/iac-state-management/spec.md`) was rewritten to forbid **computing** a workspace name from a stack's directory name while explicitly permitting the two to agree, chosen so that this change is performable rather than self-violating.

**The tree is already inconsistent in a way a reader has to be told about rather than shown.** `terraform/stacks/main-production/` declares `github_environment: production`, `read_only_secret: HCLOUD_TOKEN_PRODUCTION` and a `cloud` block naming `infrastructure-prod` — three different spellings of one stack, each correct against a different namespace and none of them the stack's own name. That is a state entry 62 entered knowingly and bounded by this entry.

**This change does owe specification deltas, and the handoff that opened it left that open.** Three capabilities state the GitHub Environment `production` by name — in an obligation (*"The `production` Environment SHALL require a reviewer"*), in scenario bodies, and in the requirement that confines the platform stack's deploy credential. Renaming the Environment makes eight requirements name an Environment that does not exist. They are corrected here rather than left to rot; the correction is to the name alone, and no obligation moves.

**A ninth requirement is corrected for a different reason, and it is the finding this change did not expect to make.** *Remote State Backend*, the queue entry, the handoff and both `versions.tf` comments all say that pushing a `versions.tf` ahead of the workspace rename makes the next plan propose creating every resource from scratch — and, on staging, apply them unattended. The sibling requirement *Workspace Execution Mode Set to Local* has always contradicted that, and the HCP organisation's `default-execution-mode` was read as `remote` on 2026-09-12, which settles it: a workspace `terraform init` creates is a remote-execution workspace with no variables, so the run fails rather than producing an appliable plan. **The ordering this change follows is unchanged and its justification is not** — what pushing early actually costs is that an empty workspace takes the name the rename needs, which is the same failure the stray GitHub Environment below already demonstrates in the other interface. `design.md` decision 2 records the measurement and its limits.

## What Changes

**Outside the repository**, by the operator, in an order this change's tasks fix and `design.md` justifies:

- **The two HCP Terraform workspaces**: `infrastructure-prod` → `main-production`, `infrastructure-staging` → `main-staging`. Renamed in the HCP interface **immediately before the branch is pushed** — which is what preserves their state, and is as late as the mechanism allows, since the local plan that checks the rename needs both the renamed workspace and the flipped `versions.tf`.
- **The two GitHub Environments**: `production` → `main-production`, `staging` → `main-staging`. Renamed between the pull request's approval and its merge, which is the narrowest window the mechanism permits.
- **The two read-only repository secrets**: `HCLOUD_TOKEN_PRODUCTION` → `HCLOUD_TOKEN_MAIN_PRODUCTION`, `HCLOUD_TOKEN_STAGING` → `HCLOUD_TOKEN_MAIN_STAGING`. GitHub cannot rename a secret, so this is create-then-delete rather than a rename, and the two names coexist across the merge.
- **The two Hetzner projects**, to the same two names. Nothing in this repository reads a project's name, and a Hetzner API token is asserted to survive its project's rename — **asserted by the queue entry and by nothing this change has measured**, which is why the rename goes last and why the confirmation carries an observation for it alone.

**An empty GitHub Environment named `main-production` already exists and blocks the rename.** It was created by hand at 2026-09-12T06:11:52Z, four minutes before `PLATFORM_DEPLOY_HOST` was rewritten, holds no secrets, carries no protection rules and has no deployment. It is the one piece of half-done state this change inherits; it is deleted first, and deleting it is also this change's cheapest probe that renaming an Environment is possible at all.

**Inside the repository**, and it is genuinely small:

- **`terraform/stacks/*/versions.tf`** — the `cloud` block's `workspaces.name`, and the comment in each saying the two names are deliberately out of step until this entry. **Deleting those comments is part of the work**, not tidying around it: they are a commitment entry 62 made, and this change is what discharges it.
- **`terraform/stacks/*/pipeline.yml`** — `github_environment` and `read_only_secret`. **Not `target_environment`**, which names the Ansible group: that is the environment axis, already spelled in full, and deliberately independent of the stack's name.
- **`ansible/inventory/main-production.hcloud.yml` and `main-staging.hcloud.yml`** — each reads its credential from an environment variable whose name **must equal** its stack's declared `read_only_secret` (*Dynamic Inventory via the hcloud Plugin, One Source per Stack*, `openspec/specs/iac-host-configuration/spec.md`). `.github/tests` compares the pair, so the two move in one commit or the build fails.
- **`.github/workflows/platform-deploy.yml`** — `environment: production`, the only literal GitHub Environment name in any workflow. The handoff that opened this change did not name it; it is found by reading the workflows rather than the documents.
- **`ansible/.envrc.example` and the repository-root `.envrc.example`** — the two exported names and the prose naming them. Every operator's own `ansible/.envrc` carries the same two names and is **gitignored, so no review and no check can catch a stale one**; the tasks say so, and say that a stale one fails the next local converge at inventory parse.
- **`.github/tests` literals** — `PROD_READ_ONLY_SECRET` and `PROD_GITHUB_ENVIRONMENT`; `SECOND_ENVIRONMENT_READ_ONLY_SECRET`, `SECOND_ENVIRONMENT_GITHUB_ENVIRONMENT` and `SECOND_ENVIRONMENT_WORKSPACE`; `GATED_DEPLOY_ENVIRONMENT`. The dead `WORKSPACE_FORM` constant goes with them: it is referenced by nothing and its comment quotes the `infrastructure-<environment>` derivation entry 62 retired.
- **A new assertion the suite does not have**: that no committed file outside `openspec/changes/archive/` names a retired external name. It is the only mechanism in this repository that can catch a name this change misses, because every other check reads the *declaration* rather than the prose around it.
- **Documents**: `README.md`, `docs/bootstrap-a-new-host.md` (a runbook, read end to end rather than grepped), `docs/deferred-work.md`, and `docs/change-queue.md` entries 52 and 70, which quote names this change moves. **Entry 60 does not**, though the handoff says it does: the only occurrences of either secret name in that file are in entries 63 and 70 (read 2026-09-12). Recorded because an unexplained absence from this list reads as an oversight.

## What Does Not Change, and Why Each One Is Named

- **`target_environment`, the Ansible groups, the `group_vars` filenames and the `--vault-id` labels.** A stack is a *(tenant, environment)* pair and a group is the environment alone. Entry 62 split those two names apart on purpose, at the cost of a new declared field; collapsing them again here would undo its whole point.
- **`HCLOUD_TOKEN` inside each GitHub Environment.** Environments namespace their own secrets, so the write token needs no qualifier — and *Credential Scoping by Privilege* (`openspec/specs/iac-cicd-pipeline/spec.md`) depends on that name being the one GitHub falls back to. The read-only secret needs the stack in its name only because *repository* secrets are one flat namespace.
- **`HCLOUD_TOKEN_MAIN_PRODUCTION` is not shortened to `HCLOUD_TOKEN_PRODUCTION`.** That is knowingly the second of two renames of the same secret. `PRODUCTION` alone stops being unique at a second tenant, and a repository secret cannot be renamed — so choosing the short form now buys one fewer character and a third rename later.
- **`PLATFORM_DEPLOY_HOST`.** Its name is correct as it stands; its *value* was corrected to `main-production` by entry 62's operator steps on 2026-09-12.
- **The `versions.tf` provider comments' claim that prod's read-only secret is `HCLOUD_TOKEN`.** That claim is already false and is `docs/change-queue.md` entry 70's work. This change corrects the half of staging's comment that names `HCLOUD_TOKEN_STAGING` — a name it moves — and leaves the `HCLOUD_TOKEN` error standing, because correcting a factual error inside a rename is the unrelated scope entry 70 exists to hold.
- **`ansible/roles/deploy_user/README.md`'s `production` Environment.** That names an Environment in *an application's own repository*, which this scheme does not reach and this change cannot rename.
- **`docs/review-2026-09-08-host-readiness.md`.** A dated review of the tree as it stood, read the way an archived record is read.
- **`docs/naming-conventions.md`'s "NOT YET IN EFFECT" banner.** It is deleted by whoever archives the last of the four entries, and entry 64 remains.
- **The archived change records under `openspec/changes/archive/`.** A record says what was decided and built at the time.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

Nine requirements across three capabilities. Eight are reached for the same reason — each states the GitHub Environment `production` by name — and for those **no obligation moves and no scenario is renamed**: each edit replaces one literal, and each requirement is reproduced whole because that is what a `MODIFIED` block requires. The ninth corrects a false rationale sentence.

- `iac-cicd-pipeline`: **two requirements.** *Gated Production Apply Applies the Reviewed Plan* names the Environment in the obligation that it requires a reviewer and in two scenario bodies. *Scheduled Workflows Report Their Own Liveness* names it in the paragraph explaining why the ping key is repository-scoped — the Environment being named is the thing that would break it.
- `iac-state-management`: **two requirements.** *HCP Terraform Access via a Static Token, Unsplit by Privilege* names the Environment-scoped half of the `TF_API_TOKEN` pair. *Remote State Backend* is the ninth: its rationale says that pushing ahead of a workspace rename makes the next plan propose creating every resource from scratch, which the measurement in `design.md` decision 2 contradicts. Its obligations are untouched — one workspace per stack, no two the same, and no derivation between a workspace's name and its directory's — and only the explanation of what the wrong order costs is rewritten.
- `iac-platform-deploy-pipeline`: **five requirements**, which is every requirement in that capability that names an Environment at all: *Pull Request Validation Runs Without Deploy Credentials*, *Gated Deploy Reuses the Terraform Production Environment*, *Reviewer Sees the Exact Diff Before Approving*, *Deploy Job Reaches the Host Over a Private Tailnet* and *Deploy Credential Confined to the Gated Job*. This capability is the one that names it most, because the platform stack deploys to production alone and its whole gate is that Environment.

**Three requirement titles keep a word this change does not rename.** *Gated **Production** Apply Applies the Reviewed Plan*, *Gated Deploy Reuses the Terraform **Production** Environment* and *Same approvers gate both kinds of **production** change* read *production* as prose — the environment, not the Environment's identifier. Renaming a requirement costs a `REMOVED` + `ADDED` pair, and a scenario title can move only where its requirement's title moves too; spending that to change prose that is already correct would be the wrong trade. Stated rather than left to a reader to wonder about.

**No requirement names a workspace, a repository secret or a Hetzner project** — not as a value, anywhere in `openspec/specs/`. *Remote State Backend* deliberately stopped deriving a workspace name at entry 62, *Credential Scoping by Privilege* names the read-only secret only as *"the read-only secret named by the stack's own pipeline declaration"*, and *Each Stack Has a Dedicated Hetzner Cloud Project* names no project. Three of this change's four external renames therefore move no specification text at all, which is what those wordings were for; the ninth requirement above is reached by its explanation of the *ordering*, not by a name.

## Impact

- **HCP Terraform**, by two renames in its interface. `infrastructure-prod` is `ws-QxowEvdjeZzziZ33`, four resources, state serial 46; `infrastructure-staging` is `ws-b2HGxWg9zz2SoCC5`, four resources, serial 4, both read on 2026-09-12 and both in Local execution mode. A rename preserves the workspace **id**, so the observation that matters is that those two ids answer to the new names and their serials have not gone backwards — which is stronger than reading a States view and is checkable from a terminal.
- **GitHub**, by two Environment renames and two secret creations. The `production` Environment holds **fifteen** secrets and one required reviewer; `staging` holds **six** and no protection rule. (The handoff that opened this change said five and two; that was written before the converge credentials landed, and the counts above were read on 2026-09-12.) A rename that silently dropped either would show up in `gh secret list --env` and nowhere else until a deploy failed.
- **Two windows in which continuous integration on `main` is broken**, both closed by the merge, and **both failing by creating something under the name the rename needs** rather than by refusing. From the HCP rename until the merge, `main`'s `versions.tf` names workspaces that no longer exist, and `terraform init` **creates** a workspace it cannot find — as a remote-execution workspace holding no variables, so the run then fails rather than applying anything, and what is left behind is an empty workspace squatting the name. From the Environment rename until the merge, `main`'s `pipeline.yml` and `platform-deploy.yml` name Environments that no longer exist, and GitHub **creates** an Environment a workflow names, **with no protection rules** — so a production job in that window would run *unreviewed*, which is the more dangerous of the two and the one that is genuinely silent. The operator's standing instruction for both is that nothing else merges to `main`.
- **Nothing on either host.** No converge behaviour, no Hetzner resource, no Compose service. The merge does trigger a converge, because `ansible/inventory/*.hcloud.yml` changes — and that converge is one of the five observations at `tasks.md` 9.1, not a side effect to tolerate.
- **`.github/tests`**, whose 846 tests are this change's largest verification surface and six of whose literals move with the tree.
