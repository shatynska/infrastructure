## Context

See `proposal.md` for motivation. Relevant existing constraints this design works within:

- `iac-platform-services` already requires monitoring to run in the same `platform/` Compose stack on the same host, deployed by the existing `platform-deploy` GitHub Actions pipeline. Ansible's scope stops at the container runtime and never touches `platform/`'s own service definitions or lifecycle — this change's one exception is the volume mount itself (§ Storage layout below), which is host-configuration territory Ansible already owns, not a `platform/` service.
- `iac-host-configuration` already establishes a private Tailscale tailnet joined by the host, currently used only for non-operator SSH access (the GitHub Actions deploy job).
- The host is a single Hetzner `cx33` (4 vCPU / 8GB RAM, 80GB local disk).
- A `main-data` Hetzner Volume (10GB) is already provisioned and attached (`terraform/environments/prod/terraform.tfvars`) but nothing currently mounts it — `postgres_data` and `traefik_letsencrypt` are plain Docker named volumes on local disk today.
- Platform secrets are sourced from outside the repo (e.g. GitHub Actions secrets rendered at deploy time), never committed — established by the existing "Platform-Level Secrets Are Never Committed" requirement.
- Applications are separate repositories that join `platform_edge` as an external network; the monitoring stack cannot assume cooperation from an application's own code — including trusting an application container with network-level read access to other applications' or the host's observability data, not only trusting it to behave well as a Traefik backend.
- `commerce-ops` is the first application deployed via this platform; several more applications, sharing a database inside the shared Postgres instance, are expected soon. How a new application gets its own database/role inside that instance is separate, already-tracked follow-up work (`platform/README.md`), not something this change resolves.

## Goals / Non-Goals

**Goals:**
- Metrics-based visibility into host health and the health of every service on the host (platform's own and any future application), with alerts routed to Slack.
- A first implementation of the dead-man's-switch mitigation already committed to in `integrate-ansible-host-config/design.md` but never built.
- Bounded, dedicated persistent storage for monitoring data.

**Non-Goals:**
- Log collection, log storage, or log-content-based alerting (Loki/Promtail/Alloy) — deferred to a follow-up change, once metrics-based alerts show what's actually noisy.
- Any per-application opt-in instrumentation (an app exposing its own `/metrics`) — remains each application repository's own future decision.
- Moving `postgres_data` or `traefik_letsencrypt` onto the `main-data` volume — out of scope; this change only starts using the volume for monitoring's own data.
- Picking the specific third-party dead-man's-switch provider or Slack app — those are operator account-setup steps, not something this change's automation provisions.

## Decisions

**Classic Prometheus/Grafana/Alertmanager stack, not an all-in-one agent (e.g. Netdata).** Explicitly requested. It also separates concerns (collection, alert routing, visualization) along lines that let the deferred log stack (change 2) slot in later as an additional Grafana data source without restructuring anything built here.

**Alertmanager owns alert routing, not Grafana's built-in alerting.** Keeps the routing/notification concern in one place regardless of which system (Prometheus now, Loki's ruler later) originates an alert, and is the natural host for the Watchdog pattern below — a well-established idiom in the Prometheus ecosystem, not something invented for this change.

**Dead-man's-switch via a permanent "Watchdog" alert.** An alert rule that always evaluates to firing (e.g. `vector(1)`), routed through Alertmanager to a receiver that pings the external heartbeat URL. As long as the whole pipeline (Prometheus → Alertmanager → network egress) is healthy, the heartbeat keeps arriving; if the host, Prometheus, or Alertmanager goes down, the heartbeat stops and the external service raises its own alert — the one property that must not depend on this host staying up.

**cAdvisor for per-container metrics.** Standard Prometheus-ecosystem exporter for container-level CPU/memory/restart/OOM signals; reads `docker.sock` read-only and host cgroups, the same trust boundary Traefik's existing Docker provider already relies on.

**Reuse Traefik's existing metrics endpoint for per-application HTTP error rates**, rather than requiring each application to expose its own `/metrics`. Traefik already knows the per-router/per-service status code breakdown; scraping it gives every current and future application 5xx-rate visibility with zero coordination.

**Storage layout:** mount `main-data` at a fixed host path (e.g. `/mnt/main-data`) via Ansible's existing host-configuration scope (a mount, not a service — consistent with Ansible stopping at the container runtime and never touching `platform/`'s services), then bind-mount subdirectories from it into Prometheus's and Grafana's containers in `platform/docker-compose.yml`. Simpler than a Docker volume plugin, and keeps the mount itself owned by the same layer (Ansible) that already owns host-level filesystem concerns.

**The volume's device path is discovered on-host, not hand-copied from Terraform.** `terraform/modules/volume/outputs.tf` exposes `linux_device`, but that's a Hetzner-computed output, not an operator-chosen input the way `ssh_allowed_cidrs` or `volume_size` are — there's no natural moment at which a human is already editing `ansible/inventory/group_vars/prod.yml` and would remember to also copy this value in, and an out-of-date copy would fail silently until the mount task ran against the wrong device. Hetzner attaches every volume at a stable, predictable `/dev/disk/by-id/scsi-0HC_Volume_<id>` path; since exactly one such device exists on this host, the mount task globs for `/dev/disk/by-id/scsi-0HC_Volume_*` and uses whatever it finds, rather than needing to know the specific ID ahead of time. This avoids introducing a Terraform-output-to-Ansible-variable sync step that doesn't exist anywhere else in this repository for a computed (as opposed to operator-supplied) value.

**Retention: bounded by both time and size.** Target Prometheus retention around 3-4 weeks by time, with an explicit size cap (e.g. `--storage.tsdb.retention.size`) as a backstop so an underestimate of cardinality can't silently fill the volume. Sizing basis: at this scale (a handful of exporters, low-thousands of active series, 15-30s scrape interval), Prometheus's own compressed storage is on the order of a few hundred MB for a month of retention — well within the 10GB volume alongside Grafana's own (small) storage. The size-based cap, not the time estimate, is what actually protects the volume if that estimate is wrong.

**Alternative considered and rejected: Netdata or similar all-in-one agent.** Lower operational overhead, but explicitly not what was wanted here — the classic stack was a deliberate choice, not a default.

**Grafana is reachable only over the existing private tailnet, not routed through Traefik.** The cloud firewall's `web_allowed_cidrs` is `0.0.0.0/0` — anything Traefik routes on its public entrypoints is internet-reachable, and Grafana has no built-in exposure-appropriate default (its own auth exists, but shipping it open to the internet on a default admin credential is not an acceptable starting state). Rather than adding new Traefik middleware (BasicAuth or an IP allowlist) to carve out an exception, Grafana binds to the host's Tailscale interface address instead of a Traefik-routed public one, reusing the tailnet `iac-host-configuration` already establishes for the deploy job. This adds no new access-control mechanism to build or maintain, and is consistent with how this repository already restricts a sensitive path to the tailnet rather than the public interface. Grafana's admin credential is also set from a secret at deploy time rather than left at its image default — belt-and-suspenders alongside the network restriction, since a tailnet-only listener is still one misconfiguration away from being reachable more broadly than intended. Alternative considered: Traefik BasicAuth/IP-allowlist middleware — rejected because it adds a second access-control mechanism (Traefik's, on top of Grafana's own auth) for no benefit over reusing the tailnet that's already there.

**postgres-exporter uses a dedicated, restricted-privilege monitoring role**, not the existing Postgres superuser credential. One more credential to provision and rotate, but the monitoring stack — which exists to catch things going wrong — does not itself need or get superuser database access. The role is granted only what `postgres-exporter`'s standard collector queries require (effectively read-only access to statistics views), not table data access.

**That role is created by a one-time manual operator step, not by this change's automation.** Neither Ansible (scope stops at the container runtime) nor `platform-deploy.yml` (renders `.env`, runs `docker compose up`) has a slot for running SQL against the already-initialized, live shared Postgres instance — and this change deliberately doesn't add one. General per-application database/role provisioning inside that shared instance is already tracked as separate, unsolved follow-up work; postgres-exporter needing its own narrow, one-time role is a small instance of a bigger problem this change is not trying to solve. The operator runs the role-creation SQL once (documented in `platform/README.md`), the same way the Slack webhook and dead-man's-switch registration are already one-time manual steps in this change. Alternative considered: automate it as a deploy-job step (e.g. `docker exec` into the Postgres container). Rejected here because it would mean building bespoke automation for this one credential ahead of the general provisioning mechanism the next several applications (which need their own shared database in the same instance) will actually need — better solved once, generally, as that follow-up work, than piecemeal here.

**Prometheus, Alertmanager, cAdvisor, node-exporter, and Grafana are placed on a new internal-only Docker network (`platform_monitoring`), not `platform_edge`.** `platform_edge` is joinable by any application repository's own Compose file (`iac-platform-services`'s "Shared Docker Network for Application Reuse" requirement); if these services sat on it, any application container — including ones not yet written — would get unauthenticated read access to Prometheus's full query API: every other application's metrics, host resource data, and container restart/OOM history.

Correction from an earlier draft of this decision: dual-homing a service onto both `platform_edge` and `platform_monitoring` does **not** isolate it — Docker does not scope a container's listening ports per network; any container sharing *any* network with another can reach every port that container exposes, published or not. A service attached to both networks is therefore just as reachable from `platform_edge` as if `platform_monitoring` didn't exist. This means dual-homing cannot be the mechanism for letting Traefik or postgres-exporter reach `platform_monitoring` while staying protected from `platform_edge` — two different, service-specific fixes replace it:

- **postgres-exporter never joins `platform_edge` at all.** Postgres instead gains a second, private-link network shared with nothing but postgres-exporter (`platform_postgres_metrics`). postgres-exporter reaches Postgres over that link and is scraped by Prometheus over `platform_monitoring`; it has no membership in `platform_edge` and is therefore unreachable from any application container. Postgres's own `platform_edge` membership is unchanged — it already needs to be reachable by every application, so this adds no new exposure to Postgres itself, only a private second path used by exactly one other container.
- **Traefik's metrics exposure to `platform_edge` is accepted, not eliminated.** Traefik must remain reachable on `platform_edge` for application routing, and — unlike postgres-exporter, which has an alternative path to what it needs — there's no equivalent private link that gets Prometheus to Traefik's metrics without either Traefik or Prometheus sitting on a network the other doesn't need. Closing this completely would require binding Traefik's metrics entrypoint to a static IP scoped to `platform_monitoring` specifically (Compose IPAM + a pinned internal address + an entrypoint bind-address flag) — a real fix, but a more fragile, higher-maintenance one than the fact it's protecting justifies at this scale: what it protects is per-application HTTP status/error-rate counts, not database contents, host resource data, or the Prometheus/Alertmanager APIs themselves (those remain fully isolated via `platform_monitoring`). Recorded as an accepted trade-off (see Risks/Trade-offs), not solved here.

**Grafana's Tailscale bind address is resolved to a literal IP by the GitHub Actions runner, from the existing `PLATFORM_DEPLOY_HOST` secret, before being rendered into `.env`.** An earlier draft of this decision proposed resolving the host's tailnet IP via `tailscale ip -4` as part of the deploy step run *on the host* — but the deploy job's only channel to the host is an SSH session bound to a forced command (`deploy-receive platform`, per `iac-host-configuration`'s "Restricted Deploy Account Supports Per-Application Forced-Command Deploys" requirement), which accepts no other command, so that can't run there. A second draft proposed rendering `PLATFORM_DEPLOY_HOST`'s raw value straight into `.env` for Grafana's port binding — but this repository's own prior design record (`archive/2026-08-20-connect-platform-deploy-via-tailscale/design.md`) documents that secret's value as either a Tailscale MagicDNS hostname *or* a literal tailnet IP, treated as interchangeable by every existing consumer (`tailscale ping`, `ssh-keyscan -H`, `ssh`) because all of them accept either form. Docker's `ports:` host-IP binding does not: it parses its `host_ip` as a literal IP address only, with no DNS/MagicDNS resolution, so a hostname there would fail Grafana's container creation and — because `app-deploy` runs `docker compose up -d --wait`, which fails the whole step on any one service failing — fail the entire platform deploy, not just monitoring.

The fix keeps the resolution off the host (still respecting the forced-command restriction) but does it on the GitHub Actions runner instead, which faces no such restriction and is already tailnet-joined for this job (`tailscale/github-action`, the "Connect to the tailnet" step). This adds one workflow step, not a new secret, and doesn't require constraining or auditing `PLATFORM_DEPLOY_HOST`'s existing, already-relied-upon format for its other consumers.

The step is written defensively rather than relying on an unverified assumption about `tailscale ip`'s exact matching behavior for an input that's already a literal IP (as opposed to its documented, precedented use resolving a hostname/FQDN): it first checks, with a full dotted-quad-validating IPv4 regex (each octet range-checked 0-255, not just "digits and dots"), whether `PLATFORM_DEPLOY_HOST`'s value already parses as an IPv4 literal. IPv4-only is deliberate, not an oversight: the same archived design record cited above documents the literal form specifically as `100.x.y.z` — Tailscale's IPv4 CGNAT range — so an IPv6 literal is not a case this secret's value can actually take. If the regex matches, that value is used as-is, with no `tailscale ip` call at all. Only when it doesn't match — i.e. it's a hostname — does the step invoke `tailscale ip -4 <value>` to resolve it. Either way, the step then fails loudly if the value it's about to write is empty or fails that same IPv4 validation, rather than writing an empty or malformed address into `.env`. This makes the fix correct regardless of whichever way `tailscale ip`'s behavior on a literal-IP argument actually turns out to be, without needing to test it against a real tailnet first.

**Prometheus's scrape/alert-rule config, Alertmanager's routing config, and Grafana's datasource/dashboard provisioning are defined inline in `platform/docker-compose.yml`, via Compose's `configs:`/`content:` mechanism, not as separate files.** The existing deploy pipeline (`platform-deploy.yml`) transfers exactly `docker-compose.yml` and `.env` to the host — `deploy-receive`'s forced extraction (`iac-host-configuration`) accepts no other archive member. There is no path for a separate `prometheus.yml`, `alertmanager.yml`, or Grafana provisioning file to reach the host under the existing, unmodified pipeline. Compose's inline `configs:` (content embedded directly in the Compose file, rendered to a file inside the container at start) keeps every byte this change needs on the host inside the one file the pipeline already delivers — the same reason Traefik's own configuration today is entirely command-line flags in `docker-compose.yml` rather than an external file. Alternative considered: extend the deploy pipeline/`deploy-receive` to transfer additional named files. Rejected as disproportionate to this change — it would mean revising an already-established, working, security-reviewed deploy mechanism (forced-command SSH, fixed archive-member allowlist) for the sake of config files that fit within the existing one-file constraint just fine.

**A Prometheus target being down is itself an alert condition**, using Prometheus's own `up` metric, not left to be noticed only via one-time deploy verification (task 2.6). This closes a gap where, for example, postgres-exporter's role being dropped or its credential rotated incorrectly after initial deploy would otherwise silently stop that metrics feed with no alert.

## Risks / Trade-offs

- [Risk] Six new containers added to a host that also runs Traefik, Postgres, and will run application containers. → Mitigation: at this metric cardinality the stack's steady-state resource use is small relative to the host's 8GB/4vCPU; revisit sizing if the number of applications on the host grows substantially.
- [Risk] `main-data` has never been mounted at the OS level before — this is new ground, not a change to something already working. → Mitigation: task sequence verifies the mount and data persistence across container recreation before anything depends on it.
- [Risk] Slack is the sole alert destination; if the webhook is misconfigured or Slack itself has an outage while the host stays up, an alert could be silently lost. → Mitigation: partially covered by the dead-man's-switch, but only for total pipeline failure, not a live Slack-side outage — accepted for this scale; revisit if this gap matters more later.
- [Risk] cAdvisor's per-container series count grows with the number of containers on the host; unexpectedly high cardinality could outpace the retention-by-time estimate. → Mitigation: the size-based retention cap bounds the worst case regardless.
- [Risk] postgres-exporter's monitoring role is created by a manual operator step rather than automation, so it could be forgotten, mistyped, or not re-created if the shared Postgres instance is ever rebuilt. → Mitigation: the new "target down" alert (see Decisions) surfaces this immediately rather than leaving it a silent gap, and the step is documented in `platform/README.md` alongside the instance's other operational notes.
- [Risk] Traefik's metrics endpoint, unlike every other monitoring service, remains reachable from `platform_edge` and therefore from any application container — accepted rather than eliminated (see Decisions). → Mitigation: what's exposed is limited to per-application HTTP status/error-rate counts already visible in each application's own access logs; no database content, host resource data, or Prometheus/Alertmanager access is exposed this way. Revisit with a static-IP-bound entrypoint if this host ever runs an application whose operator shouldn't see other applications' traffic-volume/error-rate shape.
- [Risk] Inline Compose `configs:` blocks push all of Prometheus's, Alertmanager's, and Grafana's configuration into `docker-compose.yml` itself, making that file substantially larger and mixing service definitions with their configuration content. → Mitigation: this is a direct, accepted consequence of the existing deploy pipeline's one-file constraint, not an oversight; YAML block scalars keep each config readable as a distinct section, and nothing about this prevents a future change from splitting it out if the deploy pipeline itself is ever revised to carry more than `docker-compose.yml`/`.env`.
- [Risk] Inline `configs:`/`content:` is a comparatively recent addition to the Compose Specification. The host's `docker-compose-plugin` is installed via `state: present` (`ansible/roles/geerlingguy.docker`), with no version pinned anywhere in this repository, so nothing currently guarantees the installed version supports it. → Mitigation: task 6.2's pre-completion verification includes confirming the host's `docker compose version` supports inline `content:` configs, so this surfaces before it can fail a production deploy; low probability given the host was provisioned recently, but previously unverified.

## Migration Plan

Mostly additive: new services in `platform/docker-compose.yml`, a new host-level mount added via Ansible, and new GitHub Actions secrets — deployed the same way Traefik and Postgres already are. Three existing-service changes are involved, all additive rather than behavioral: enabling Traefik's metrics endpoint (a command-line flag) and attaching it to the new `platform_monitoring` network alongside its existing `platform_edge` membership, and attaching Postgres to the new `platform_postgres_metrics` network alongside its existing `platform_edge` membership. Rollback is removing the new services and networks from the Compose file (and reverting Traefik's flag and both services' added network memberships) and redeploying; monitoring data on `main-data` is unaffected by container removal since it's a host bind mount, not container-scoped storage. The new `platform-deploy.yml` workflow step that resolves Grafana's bind address is harmless to leave in place even after such a rollback (it computes a value nothing then reads), but should be removed alongside the Compose changes for a clean revert.

## Open Questions

- Exact alert thresholds (5xx rate %, restart-count window, disk/CPU/memory percentages) are not fixed here — specs require that these alerts exist and are configurable, not specific numbers. Set conservative initial defaults during implementation and tune once real traffic/behavior is observed; this can change later without a spec change.
