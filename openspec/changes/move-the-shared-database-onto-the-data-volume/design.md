## Context

Measured on both hosts on 2026-09-16, because the shape of the store decides how it is moved:

- The container is `postgres:18.6`, started as `root` and stepping down to uid/gid 999 by its own entrypoint. `.Config.User` is empty, which is what makes the entrypoint able to create and own what it needs inside a bind mount.
- Inside the store, `/var/lib/postgresql` is `1777` owned `999:999`, `18/` is `0755` owned `root:root`, and `PGDATA` — `18/docker` — is `0700` owned `999:root`. The stack mounts the **parent**, not `PGDATA`, and `platform/docker-compose.yml` already carries the reasoning: from 18 the image declares `VOLUME /var/lib/postgresql` so that `pg_upgrade --link` does not cross a mount boundary, and mounting the old `…/data` path makes the entrypoint refuse.
- `platform_postgres_data` is 70 MB on production and 72 MB on staging. `/mnt/main` is 9.8 GB with 949 MB used on production and 623 MB on staging. Prometheus is capped by its own flags at 28 days and 4 GB.
- The deploy runs `docker compose pull` then `docker compose up -d --wait` inside `app-deploy`. There is no `down`, and no `-v` anywhere in the path, so an unreferenced named volume is not removed by deploying. The host's periodic reclamation is `image_prune` and reaches images, not volumes.
- `host-converge.yml` triggers on `ansible/**`; `platform-deploy.yml` triggers on `platform/**`, with no exclusion for Markdown. A change to `group_vars` and a change to anything under `platform/` therefore start different workflows, which is what makes the sequencing below expressible as two merges — and it is also why `platform/README.md` belongs in the second pull request rather than the first: editing it is a `platform/**` push and would deploy.

## Goals / Non-Goals

**Goals:**

- The shared instance's data lives at `/mnt/main/postgres`, created by the converge with the ownership the image expects, and the instance comes up on the data it already had.
- No application's database is re-provisioned, and no application's credentials are rotated, as a consequence of this change.
- The old store remains intact and reachable until the operator removes it deliberately, so that the move is reversible by re-pointing one line.

**Non-Goals:**

- Moving `traefik_letsencrypt`. It is 48 KB, its contents are re-issued on demand by the certificate authority, and nothing about it grows. Moving it would be motion without a reason, and the change that declared both a Non-Goal is not owed a symmetrical answer.
- Building the backup the operator intends to add. It is a change of its own, and this one does not depend on it: the store needs no backup under its current classification, before the move and after it.
- Changing what the shared instance is permitted to hold. *Single Shared PostgreSQL Instance, Per-Application Databases* is untouched, and its unconditional prohibition on durable data is what this change's safety rests on.
- Automating the copy. It happens once per host, under supervision, and a mechanism that exists to run twice in this repository's life would have to be maintained forever.

## Decisions

**A bind mount under `/mnt/main`, not a Docker volume with `driver_opts` pointing at the volume.** The bind mount is what Prometheus and Grafana already use, so the subdirectory mechanism, the ownership convention and the on-host legibility all carry over unchanged. A local-driver volume with a `device` option would reach the same filesystem while hiding the path behind a volume name, and would leave `docker volume ls` showing two entries that differ only in where they land. Rejected for that.

**The host directory is created by `platform_data_volume`, owned `999:999`, mode `0755`.** Ownership matches the image's own user, exactly as Prometheus's subdirectory carries 65534 and Grafana's 472, and that is the existing convention rather than a new rule. Mode `0755` rather than the image's `1777`: the sticky, world-writable mode upstream exists so the image can run as an arbitrary uid, which this stack does not do — the container starts as root and the entrypoint creates `18/` and `18/docker` beneath, as it does inside the named volume today. `PGDATA`'s own `0700` is created by `initdb` and is not this directory's business.

**Two pull requests, with an attended copy between them, and the converge first.** This is the load-bearing decision.

A single merge would start the converge and the deploy together with nothing sequencing them, and the copy has to happen after the directory exists and while the instance is stopped. The window is not schedulable inside one merge. Worse, the deploy winning the race is not loud: Docker creates a missing bind source as an empty root-owned directory, the entrypoint finds no `PG_VERSION` under it, and `initdb` makes a **new empty cluster**. The stack then comes up healthy, `--wait` is satisfied, and `commerce-ops` meets a database that does not exist. Nothing in the deploy's output says what happened.

That is worth contrasting with the ordering hazard `move-the-platform-data-mount` recorded, because they are not the same failure. There, a wrongly ordered deploy left Prometheus and Grafana writing to shadowed directories — loud, and repaired by re-running the deploy with no data lost. Here the wrong order **initialises** a store, and the repair is a copy over a cluster that already exists rather than into an empty directory.

**What each pull request carries is decided by which tree the assertions are true of, not by subject.** The first carries the inventory entry and the planning artifacts; the Compose change, the static assertions and the documents all go in the second. An assertion rewritten against the new bind source is false of a tree whose Compose file still declares the named volume, and `pr-validation.yml` runs the static suite as a required check — so splitting them by subject would make the first pull request unmergeable, and forcing it through would leave the trunk red for every pull request in flight. The cost taken instead is that the first lands an inventory entry with no assertion behind it for the length of the window, which is bounded by this change's own life. The documents follow the same rule for a second reason: `platform/README.md` describing the new reset location while the live store is still the named volume would send an operator to clear a directory nothing binds.

The split is also safe in the direction a split usually is not: between the two merges the host carries an empty `/mnt/main/postgres` that nothing binds. That is inert. The window `move-the-platform-data-mount` refused to create — a live mount absent from `fstab`, fatal at the next reboot — has no analogue here.

**The copy is a file copy of a stopped cluster, not a dump and restore.** With the instance stopped, `cp -a` of the store's contents is exact: every database, role, password hash and setting, in one step, with no credentials needed and nothing to enumerate. A `pg_dumpall` would migrate *content* rather than the store, would need the superuser password at the shell, and would have to be checked database by database. Run as a container mounting both stores, so that ownership and modes are preserved without the operator's shell needing to be root over the Docker volume's path:

```sh
docker stop platform-postgres-1
docker run --rm -v platform_postgres_data:/src:ro -v /mnt/main/postgres:/dst postgres:18.6 sh -c '
  cp -a /src/. /dst/
  for d in /src /dst; do find "$d" -type f -printf "%s\n" | awk -v d="$d" "{n++; s+=\$1} END {print d, n, s}"; done
  chmod 0755 /dst
  stat -c "%u:%g %a %n" /dst /dst/18/docker && cat /dst/18/docker/PG_VERSION'
```

**The image is the one the stack already pins**, rather than a general-purpose one fetched for the occasion: it is present on both hosts because it is what the instance runs, it carries the three tools the command depends on — `cp`, GNU `find` with `-printf`, and `awk` — and it is pinned by the same line that pins the database. A separate tag would be one more thing to pull at the worst moment and one more version nothing in this repository governs.

**The container binds the store and never `/mnt/main`.** The copy's destination and the reset recipe's target are both one path component from Prometheus's and Grafana's data, and a recursive operation rooted at the mount reaches all three. Binding only `/mnt/main/postgres` means the container has no path to the others even if a command inside it is wrong. **This is debt the change introduces rather than a hazard it removes**, and the distinction is worth keeping straight: `docker volume rm platform_postgres_data` could not reach Prometheus's or Grafana's data *by construction*, where a container given the bare mount can destroy all three, and what stands between is a sentence in a document. The narrow bind narrows it; what closes it is an assertion, which this change adds to the module that already reads that recipe rather than leaving it to prose.

**Every ownership check in this plan reads `stat`, never `ls`.** `ls` resolves ids to names, and on these hosts uid 999 prints as `deploy` and gid 999 as `systemd-journal` — so a check written as "owned `999:999`" against `ls -lad` output can never be satisfied as written, and `/mnt/main/prometheus` already prints `nobody nogroup` for the same reason. At a live gate that is the ambiguity this plan spends a paragraph removing, reintroduced by the verb.

**The `chmod` at the end is not housekeeping.** `cp -a` of the source's own root carries that root's attributes, and the source's `/var/lib/postgresql` is `1777` where the converged directory is `0755` — so without it the destination's mode after the copy is ambiguous, and an operator at a live gate meets a check that fails with a footnote saying it is fine. Setting it explicitly makes `0755` owned `999:999` the exact expected reading, and it is what the next converge would restore anyway.

**The completeness check is a file count and the byte total of regular files, per side**, because the checks that read like completeness are not: a truncated copy still carries `18/docker/PG_VERSION`, and a container that starts is a container over whatever files it found. It is deliberately **not** `du -sb` over the two trees: a directory's apparent size reflects its own growth history and differs between filesystems, so an exact copy can report a few kilobytes of difference — and the decision that reading feeds is *abandon and re-provision*, so a false positive there destroys a good copy under time pressure. Counting only regular files takes directory entries out of the comparison.

**Only `postgres` is stopped, and `postgres-exporter` is deliberately left running.** It holds no data and takes no lock on the store, so stopping it buys nothing — while stopping it takes its Prometheus target down and fires `MetricsTargetDown` (`up == 0`, `for: 5m`) within five minutes, for the whole window, which on production is the length of an approval wait. Left running it serves `/metrics` with HTTP 200 and `pg_up 0`, its container stays healthy and its target stays up, so no alert fires — the property `platform/README.md` records for the upgrade window and the same one that `docs/backlog.md` `alert-on-the-exporter-being-unable-to-read-postgres` exists to change. When that entry lands, this window starts paging and this paragraph is what needs revisiting.

**The containers are addressed by name rather than through `docker compose`, and that is not a style choice.** `/opt/platform` is `deploy:deploy` mode `0750`, and `ops_user` grants an operator account the `docker` group and never `deploy` — so an operator cannot read the Compose file `docker compose` would need. `platform/README.md`'s upgrade procedure already runs this way and says why; this change follows it rather than inventing a second convention.

Stopping first rather than copying live is not optional. PostgreSQL recovers from a crash-consistent copy the way it recovers from a power cut, which is a property to rely on when there is no choice, and this is a case where there is one.

**On both hosts, uid 999 is `deploy` and gid 999 is `systemd-journal`, and that is a consequence of this move rather than a choice available to it.** Measured on 2026-09-16: `getent passwd 999` returns `deploy` on production and staging alike. The `postgres` image runs as uid 999, so the store's files carry uid 999 on the host whatever this change does with the parent directory's ownership — the numbers are the image's, not this repository's.

What changes is reachability, not ownership. Today the store sits under `/var/lib/docker/volumes/`, and `/var/lib/docker` is `0710 root:root`, so `deploy` cannot traverse to files it nominally owns. At `/mnt/main/postgres` it can: the deploy account reads and writes every application's database files directly. `deploy` is what each application's deploy key and the platform's own key SSH in as, under a forced command.

**Recorded and accepted rather than mitigated**, on the operator's stated position that nothing here is worth building extra protection for. Two things make that defensible rather than lazy. `deploy` already writes each `/opt/<app>/docker-compose.yml` and invokes `sudo app-deploy <app>`, so it has a path to privilege on this host regardless — this narrows a gap that is already open rather than opening a new one. And the alternative was examined: `root:999` with mode `0750` would let the container's postgres traverse by group while denying `deploy`, which is neither its owner nor in gid 999 — it is the mitigation to reach for if this ever matters, and it is not free, because it departs from the ownership the image itself uses and would have to be proven against a `pg_upgrade` path this repository does not currently take. **The one thing that would not help is tightening the mode**: `deploy` *is* uid 999, so any permission the owner has, it has.

**The copy runs inside an announced maintenance window, using the mechanism that already exists for one.** `/var/lib/platform-maintenance/shared-postgres-window` is what an application's database probe reads to answer `window-open`, so an application that consults it before delivering declines to deliver while the file is there — *An Application Can Probe Its Own Database Through a Read-Only Forced Command* (`openspec/specs/iac-host-configuration/spec.md`). The instance is stopped for this copy exactly as it is for a major-version upgrade, so the same announcement applies and skipping it would make this change the first shared-instance outage that does not announce itself. The file is created before stopping the instance and removed after the databases have been verified at the new location.

**The second pull request is opened as a draft and marked ready only once both hosts have been copied.** One merge reaches every stack: staging's Environment requires no reviewer, so its deploy starts immediately, while production's waits for an approval. A merge taken before staging has been copied re-points staging's instance at an empty directory and initialises it there, unattended, with nothing between the merge and the loss. The draft state is the gate, rather than a warning in the pull request body — this repository has already had a body warning fail to stop exactly such a merge, and `platform/README.md` reaches for the same draft gate for the same reason.

**The copy is only exact while nothing writes to the source after it, and nothing in this repository enforces that.** `platform-deploy.yml` fires on **any** push touching `platform/**` and on a manual dispatch, and `app-deploy` runs `docker compose up -d --wait`, which **starts containers an operator stopped**. So an unrelated merge — a documentation edit under `platform/` is enough — restarts the instance on the old store mid-window, and every write after that point is lost when the second pull request's deploy switches to the copy. Nothing is red: the databases exist at the new location, so the database-level verification passes, and what is missing is only what was written in between.

Two guards, because the second is the one that holds: before merging, confirm no other `platform/**` pull request is ready to go; and on each host, read `docker inspect -f '{{.State.StartedAt}} {{.State.FinishedAt}}' platform-postgres-1` and re-copy if the container started after the copy. The first is a convention and this repository has already recorded that conventions of exactly this shape do not hold — `docs/backlog.md` `hold-every-platform-deploy-for-the-length-of-a-window` is the entry for the mechanism that would. The second is a reading of the host, which is why it is a task rather than an instruction.

**The converge-before-deploy order is not only prudence here — it is obliged.** *Platform Data Volume Is Mounted at a Fixed Host Path* (`openspec/specs/iac-host-configuration/spec.md`) requires the subdirectories a `platform/` service depends on to exist, with the ownership that service requires, **before that service can rely on them**. The sequencing below is what discharges that obligation for a third store; it is not this change's invention.

**The old named volume is left in place, and removed later by hand.** `docker compose up -d --wait` does not remove an unreferenced volume and `image_prune` does not reach volumes, so it survives on its own. It is the rollback: re-point the Compose file and the instance is back on the original bytes. It is removed after the operator has confirmed the new location on both hosts — a separate, deliberate `docker volume rm platform_postgres_data`, which is a task in this change rather than something the deploy does.

**The instance leaves the reach of the server's automatic backups, and that is recorded rather than mitigated.** Hetzner's backups image the root disk and not the attached volume. Today that snapshot is the only copy of anything on this host, and the shared instance is inside it by accident of where it was left, not by design — nothing claims it, no restore of it has been rehearsed, and rolling the whole server back is the only way to reach it. After this change it is outside that snapshot. The store's classification is unaffected, because it holds no durable data and is re-provisioned rather than restored, and the delta states the consequence so a later reader does not mistake the snapshot for a net under a store it never covered selectively. The operator's intended backup makes that moot; this change does not wait for it.

**Network-attached storage for a database, and why the comparison that settles it is Supabase rather than the root disk.** `/mnt/main` is a Hetzner volume — network block storage — where the root disk is local NVMe, and a database's `fsync` at commit is where that difference shows. Measured against the *alternative this system actually uses for data that matters*, it is noise: durable data is bound for an external managed service reached over the network, whose client round trip is larger than the storage difference by an order of magnitude, so any workload that tolerates that path tolerates this one without noticing. The operator made this point and it is correct; the earlier draft of this decision treated the volume's latency as a standing risk, which was inconsistent with accepting a remote managed database for everything durable.

What the comparison does **not** cover, stated so it is not rediscovered: it holds for data that could have gone to the managed service — the durable class. The shared instance exists for the other class, and a non-durable workload with a high commit rate — a session store, a job queue writing many small transactions a second — would meet the volume's `fsync` cost and was never a candidate for the remote service, so the reasoning does not transfer to it. Nothing on either host is near that today. That workload is what would falsify this decision, and the remedy is the same one-line revert the retained volume already affords.

**What the data is actually worth today, stated by the operator on 2026-09-16 and recorded here because it decides how much machinery this change is owed.** No database on either host holds production data anyone would miss: the project is at an early stage and what is there is test and text data, **production included and confirmed as such by the operator**, with one internal table there due to be removed shortly. The change is therefore one change over both stacks rather than a staging trial with a production sequel — which is also what the mechanism forces, since one Compose definition is deployed to both. So nothing in this plan is built to protect the bytes, and none of it should be read as doing so.

That does **not** make the copy optional, and the reason is worth stating because the intuition runs the other way. Without it the instance initialises empty, and the recovery is a re-provisioning per application per host with `rotate=yes` — which generates a password, writes it into that application's GitHub Environment **in another repository**, and needs that application's next deploy to pick it up. Skipping a single command on the host buys a cross-repository credential rotation. The copy is the cheap path, not the careful one.

What the statement does change is the response to trouble: **abandoning is the first-class answer, not the last resort.** Counts disagree, the cluster will not start, anything odd at all — clear the destination, let it initialise, re-provision. Nothing here is worth diagnosing under a window. What stays is the machinery that prevents a host coming up empty *silently and unattended* — the converge-before-deploy order, the draft gate, the reading of `StartedAt` — because what that costs is not bytes but an application down with nothing saying why, and the same cross-repository re-provision to recover.

It changes no requirement. *Single Shared PostgreSQL Instance, Per-Application Databases* forbids durable data there unconditionally, so this is the instance being within policy rather than an exception being made for it.

**Abandoning a bad copy is cheaper than repairing one, and that is worth knowing before the window rather than during it.** The store is classified as needing no backup and every database in it is re-provisionable by the recipe in `docs/onboard-an-application.md` with `rotate=yes`. So if a copy is found incomplete, the supported move is to clear the destination and let the instance initialise empty, then re-provision — not to reconcile two clusters under time pressure. The copy exists to avoid that work, not because the data could not be recreated.

**One thing this change cannot express, recorded rather than left as a surprise.** `openspec validate` treats a retitled scenario inside a `MODIFIED` block as a dropped one, so a scenario's *title* cannot be changed by a delta. Exactly one title is left stale by this change: *The declaration survives the volume being discarded*, in `iac-host-configuration`, whose WHEN is restated against the store while its title still names the form. `iac-platform-services`'s *The announcement outlives what it announces* was already form-independent, which is why only its WHEN needed restating. The normative content is what any reader or check consumes and it is form-independent in both; the one title is not, and `docs/backlog.md` `sweep-the-stale-scenario-titles-and-check-them` is the entry that owns that residue.

## Risks / Trade-offs

- **The deploy merged before the converge has run.** Mitigated structurally by the two-PR split and by the draft gate: the second pull request exists from early on, so that its checks can be green before either host is touched, but it cannot merge while it is a draft and it is marked ready only after both copies are verified. If the order were broken anyway, the recovery is to stop the instance, clear `/mnt/main/postgres`, copy again from the retained volume, and redeploy.
- **The copy is performed against a running instance.** A crash-consistent copy would very likely recover and would very likely be fine, which is precisely what makes it a bad habit. The task list stops the services first and the verification reads `18/docker/PG_VERSION` and the database list, not merely that the container is healthy.
- **A `--wait` deploy passes against an empty cluster.** Healthy and empty are indistinguishable to the deploy. The verification is therefore at the database level — each expected database present, and `commerce-ops` able to connect — rather than at the container level.
- **Production is down for longer than the copy, and longer than the previous two drafts of this line admitted.** The copy is seconds at 70 MB. The instance then stays stopped until production's deploy reaches it, which is: marking the pull request ready, its checks, the merge, **staging's deploy, and staging's database-level verification** — which gates production's approval and is operator-paced — and then production's own Environment approval, which this repository has seen wait hours. Every one of those is inside production's stop, and `commerce-ops` is offline for all of it. It is the only application affected, being the only one with a database in the instance.

  **Why production is copied before the merge rather than during its approval wait, since copying it later would shorten this.** Once the trunk names the bind, any `platform/**` push and any dispatch of `platform-deploy.yml` — including the rebuild redeploy `docs/bootstrap-a-new-host.md`'s Appendix B prescribes — reaches production unattended and initialises an empty cluster there. Copying production last would trade an attended outage for an unattended loss, which is the same trade the draft gate refuses for staging. The outage is the price of that, and it is paid knowingly.
- **A bind mount carries a standing hazard a named volume did not: if `/mnt/main` is not mounted when the deploy runs, Docker creates the source on the root disk and the instance comes up healthy and empty.** This is the same mechanism that shadows Prometheus's and Grafana's directories, and the consequence differs in kind — theirs is an empty dashboard, this one is an instance with no application databases in it. What bounds it is *Platform Data Volume Is Mounted at a Fixed Host Path* (`openspec/specs/iac-host-configuration/spec.md`), which obliges the mount to persist across a reboot without intervention and the converge to fail rather than proceed on a host whose volume is absent. It is recorded here because it is a failure that would be diagnosed at the database, far from the mount that caused it.
- **The window is quiet in the alerting, and that is a property being relied on rather than a guarantee.** With only `postgres` stopped, nothing in the platform stack alerts for the instance being gone — the exporter keeps its target up and reports `pg_up 0`, for which no rule exists. That is what makes an hours-long production window tolerable without a silence, and it is also exactly the gap `docs/backlog.md` `alert-on-the-exporter-being-unable-to-read-postgres` proposes to close. Whoever lands that entry makes this window page for its whole length on every stack, and this plan's announcement step is one of the places that then needs rewriting.
- **The volume becomes a single point of loss for three stores instead of two.** It is one attached device, and nothing replicates it. That is the same exposure Prometheus and Grafana already carry, extended to a store classified as needing no backup, so it changes the blast radius of a volume failure without changing what any classification promises.
